三、待裁定的架构冲突（不影响本图形态，但影响开发方式）

uni-admin 现成页面的取数方式是 <unicloud-db :collection="…">，即客户端 JQL 直连数据库； 而 DATA_MODEL.md §1 规定 19 张 grouporder-* 表的 permission 全部为 false，一切读写走云函数。 两者不兼容——所有业务页面不能用 unicloud-db + uni-table 的零代码组合，须自行调云对象取数再喂给 uni-table，分页与列头筛选也要自己接。 system/user/* 等页面不受影响（uni-id-users 是另一套权限体系）。 本图按「业务页走云对象」绘制（表格形态一致，差别只在数据来源）。详见 ADMIN_REUSE_MAP §5，提请产品与架构裁定后写入 DATA_MODEL。

四、九条红线（图注角标 红线… 即指本表）

#内容v3 状态
①一切默认脱敏作废（D-072）。编号不重排，留空缺，否则既有图注角标与其他文档的交叉引用全部失效
②业务状态与治理状态必须并列，不能合并保留。运营下架不改写团长的业务状态
③运营不得代替团长经营保留（OPS §2.2）。D-072 未触及
④二次验证不是登录作废（D-072）。二次验证整体取消，A-11 随之取消，grouporder-ops-verify 表停用
⑤统计指标只能用白名单里的词保留。不出现销售额、实收金额、GMV
⑥菜单按权限展示保留。菜单由 opendb-admin-menus 按 permission 过滤
⑦审计日志不可修改删除保留（OPS §13）。超管同样没有编辑与删除按钮
⑧Excel 审计不提供下载作废（D-072）。A-13 可直接下载清单，但须重新校验权限并换取新的临时地址
⑨不脱敏，但每一次查看和导出都必须入审计本版新增。D-072 取消脱敏，约束并没有消失，只是换了形式：原来靠「看不见」来防，现在靠「看得见但全记录」来防。凡展示完整姓名、电话、地址或提供导出的屏（A-04、A-05、A-06、A-07、A-12、A-13、A-16），图注都点明这一次访问会入审计
「既不脱敏也不提审计」是本次修订最容易犯的错——那等于把 D-072 读成「运营后台对数据没有任何约束」，而 D-072 的原文把审计链路完整保留了下来。 日志本身仍不记录密码等凭证，也不记录可继续使用的下载地址（D-071③）。

第一组 · 登录与访问控制（A-01、A-02）

A-01 是现成页面，本屏用于确认改配置后的形态；A-02 是访问结果页，表达账号停用、权限不足、会话失效、对象已变化四类被拒绝的场景。D-072 取消了二次验证，原先画在本组的验证弹窗已整体移除。

第二组 · 工作台与检索（A-03、A-04）

A-03 是在现成的 pages/index/index.vue 上改造——把 uni 统计的设备/用户概览换成 D-070 的三档待办，保留其 uni-notice-bar 与 .uni-stat--x 卡片结构。A-04 是新建页，但筛选全部走 uni-table 的列头，不再另起筛选表单区。

第三组 · 只读运营统计（A-05、A-06）

容易误以为能复用 pages/uni-stat/*——那 20 多个页面是 uni 应用统计（设备、留存、错误、支付），数据源是 uni-stat-* 表，与业务数据不通，只能复用卡片与图表组件，不能复用数据层。

第四组 · 内容治理（A-07、A-08、A-09、A-10）

后台的主链路，四屏全部新建——模板不可能自带业务治理页面。但表格、表单、弹窗、提示条一律复用 uni-admin 组件，形态与 system/* 各页保持一致。

第五组 · 账号、申诉与审计（A-12、A-13、A-14）

原第五组的 A-11「敏感资料受控查看」已随 D-072 整屏取消——不再有解敏申请、授权范围与二次验证这一套链路，需要看的字段各业务页直接展示。编号不重排，A-11 留空缺（与 UX_FLOW_SPEC §3.2 一致）。本组余下三屏都与「留痕」有关：申诉的处理留痕、Excel 事件的下载留痕、以及审计日志本身。

第六组 · 账号权限与隐私事项（A-15、A-16）

本组含唯一一屏「复用既有页 + 五处必改」的 A-15。这是 uni-admin 自带能力与本项目规则冲突最集中的地方——照搬会直接违反 OPS 与 D-029。
