## 阶段 1 · 云函数基础设施

**为什么先做这个**：OPS 有两条贯穿全部页面的硬约束——每次提交重新鉴权（§3.1）、全部操作入审计（§13）。若不在基础设施层强制，13 个页面里必然有遗漏，而且事后补比一开始做贵得多。（原第三条「默认脱敏」已由 D-072 取消。）

### 1.1 产出物

```
uniCloud-alipay/cloudfunctions/
├── common/grouporder-common/        公共模块 14 个，清单与职责见 CLOUD_API §3
├── grouporder-*-co/                 7 个云对象（两端共用），方法清单见 CLOUD_API §1.1
├── grouporder-check-callback/       图片检测回调
└── grouporder-task-*/               3 个定时任务（自动截止、导出清理、留存到期）
```

### 1.2 四个基础能力的规格来源

| 能力 | 必须实现 | 规格位置 |
|---|---|---|
| **鉴权** | 以**操作提交时**的最新账号状态与权限为准，不依赖进入页面时的结果；账号停用/权限撤销立即失效 | OPS §3.1、§12.2 |
| **审计日志** | 9 个必含字段：日志编号、操作时间、操作账号 + **当时生效的角色**、动作类型、结果、对象类型与标识、关联事项、原因摘要、操作前后状态（无变化时明确记录）、请求唯一标识 | OPS §13；`DATA_MODEL.md` §10.8 |
| **分页约定** | 统一入参 `{page, pageSize, filters, orderBy}`、出参 `{list, total}`；对接 `uni-table` 的 `@filter-change` / `@sort-change` | ADM-19 方案甲的直接后果 |
| **错误码** | 区分：无权限 / 对象不存在 / 状态已变化 / 重复提交 / 会话失效，前端据此分别提示 | OPS §12.2 |

### 1.3 幂等与并发

OPS §12.2 要求「重复提交返回第一次成功结果或当前最终状态，不重复下架、恢复、解绑、授权或限制发布」。基础设施需提供统一的幂等键机制，业务方法直接复用。

### 1.4 阶段 1 验收

- [ ] 一个 `ping` 方法：`ops-super` 账号与已停用账号分别调用，停用账号被拒绝且拒绝也写入审计
- [ ] 审计日志 9 字段齐全，`operator_roles` 记录的是调用当时的角色
- [ ] 导出与查看完整数据同样写入审计，日志中不含密码等凭证与可继续使用的下载地址

## 阶段 2 · 第一个纵切与测试数据

### 2.1 A-15 运营账号页（推荐的第一个页面）

**选它的理由**：纯前端裁剪，不需要业务云对象，一天内能完成，且直接验证阶段 0 建立的权限模型是否正确。

五处必改见 `ADMIN_KNOWN_ISSUES.md` §2.1（ADM-02、04、05、06、07）。

### 2.2 测试数据种子

**问题**：后台治理的对象（活动、商品、订单、举报）都由 client 产生，而 client 尚未开工。若等 client，后台开发要停摆。

**做法**：写一个**仅测试环境可用**的种子云函数或本地 JQL 脚本，造出覆盖各状态的数据——

| 对象 | 需覆盖的状态 |
|---|---|
| 活动 | 草稿 / 审核中 / 进行中 / 已截止 / 已取消 × 治理正常 / 已下架；含「进行中 + 已下架」组合 |
| 商品 | 在售 / 停售 × 治理正常 / 已下架；`ever_ordered` 0 与 1；`total_stock` 0 与正整数 |
| 订单 | 有效 / 已取消 / 已作废；送货上门与自提各若干 |
| 举报 | 5 种状态各一条；含指向同一活动的多条 |
| 内容检测 | 文本通过 / 命中；图片待检 / 通过 / 已拦截 |

要求**幂等**（可重复执行不产生重复数据），且**绝不可上传到生产服务空间**。

## 阶段 3 · 业务页面分六批

批内按序，批间大体独立。每批产出「云对象方法 + 页面 + 菜单挂接」。

| 批 | 页面顺序 | 核心难点 |
|---|---|---|
| **A · 治理主链路** | A-07 详情 → A-09 下架/恢复 → A-08 举报 → A-10 发布者处置 | 双状态独立；**下架须反写商品库 `governance_blocked`（D-064，两条匹配取并集、软删记录同样封禁）**；恢复的三种禁止情形 |
| **B · 发布审核** | A-17 审核 → A-18 平台配置 | 结论绑定**提交时固化的内容版本**；图片异步检测不阻塞放行（D-058）；配置改动只影响之后新提交的审核（D-057） |
| **C · 检索与统计** | A-04 检索 → A-05 统计总览 → A-06 下钻 | 结果直接展示完整数据（D-072），但每次查询与导出均入审计；指标白名单；**实测聚合耗时**（ADM-21） |
| **D · 账号与隐私事项** | A-12 绑定申诉 → A-16 隐私事项 | 双方均有业务数据时不受理；三年期限只读，运营不能延长或缩短 |
| **E · 审计** | A-13 Excel 事件 → A-14 操作日志 | A-13 **可以下载清单**（D-072），但下载须**重新校验权限并换取新的临时地址**，页面不得显示或复用日志中的历史地址（D-071③）；**不提供「重新生成」入口**，下载**不单设权限点**、随 `ops-audit-export`（D-073）；A-14 无增删改，`action_type` 用 `DATA_MODEL §10.8` 的枚举名；与登录日志分页不合并（ADM-13） |
| **F · 工作台** | A-03 | **必须最后做**——三档待办的条目来自前五批的对象状态，前面没完成就拼装不出来 |

# 第二部分 · 给写码 Agent 的投喂规范

## 核心原则

`docs/` 现有 **5000+ 行**正式文档加三份新架构文档。**整包丢给 Agent 是最差的做法**——上下文被淹没，关键约束反而被忽略。正确做法是**分层投喂 + 一张任务卡**。

| 原则 | 说明 |
|---|---|
| **引用章节，不是引用文件** | 写「OPS §6.1、D-064」，不写「读一下 OPS_ADMIN_REQUIREMENTS.md」 |
| **一次一个任务** | 一个页面或一组云对象方法。不要一次派 6 屏 |
| **每次都带 L0 底座** | 三条铁律不重复声明，就会被违反 |
| **先方案后代码** | 项目既定流程：分析 → 方案 → 确认 → 改代码 → 自查 → 总结 |
| **陷阱要点名** | 把该任务相关的 ADM 编号列出来，不要依赖执行者自行翻阅全部条目 |

## 三层投喂结构

```
L0 底座    每次必给，约 400 字，固定不变
   ↓
L1 规格    按任务选，精确到章节与 D 编号
   ↓
L2 参照    既有代码文件路径 + 效果图屏号
```

## L0 · 固定底座（每次任务原样附上）

> **项目**：群接龙购物小程序的**平台运营后台**（uni-admin + uniCloud）。它服务平台治理，**不服务团长经营**。
>
> **事实优先级**：`DECISIONS.md` → `PRD.md` / `OPS_ADMIN_REQUIREMENTS.md` → UX / 架构方案 → 子项目 README → 框架默认行为。冲突时按此顺序取信。
>
> **三条铁律**：
> 1. **不脱敏，但全量审计**（D-072）——列表、详情、搜索结果一律直接展示完整的姓名/电话/地址，不做掩码、不设二次验证、不限制导出；代价是**每一次查看与导出都必须写入审计日志**，且日志本身不可修改删除、不记录密码等凭证与可继续使用的下载地址。
> 2. **业务状态与治理状态独立并列**——活动同时持有业务状态（草稿/审核中/进行中/已截止/已取消）与治理状态（正常/已下架），**相互不改写**。一个活动可以是「进行中 + 已下架」。禁止合并为一个状态字段或一个标签。
> 3. **运营不得代替团长经营**——全站不得出现创建/编辑/取消活动、增删改商品、改价格库存限购截止时间、新建或修改订单、改统计数字的入口。运营只能：审核、下架、恢复、警告、限制。
>
> **删除类操作**（D-074）：运营账号、角色、权限点、菜单四类配置实体的删除，一律弹二次确认窗、要求逐字输入 `delete` 才执行，输入不匹配时确认按钮禁用；停用与删除分开呈现；删除写入审计且日志不随被删对象删除。业务数据没有删除入口。
>
> **数据访问**（D-075）：18 张 `grouporder-*` 表的 schema `permission` 全为 `false`，**客户端不可直连**。所有业务数据读写走云对象，`uni-table` 手动喂数据。不要写 `<unicloud-db :collection="grouporder-*">`。
>
> **工作方式**：先输出实施方案等确认，再改代码；改完自查空值风险、生命周期、命名、项目规范。**发现规格矛盾或缺口先提出，不要自行裁决**——项目既定规则是「项目文件是唯一事实来源，聊天内容只有写入文档并经确认后才成为项目结论」。

## 三张示例任务卡

### 示例 A · 云函数基础设施（阶段 1）

```markdown
## 任务：grouporder-common 公共模块 + grouporder-ops-co 云对象骨架

### 范围
做：四个基础能力——鉴权、审计日志、分页约定、错误码；
    外加一个 ping 方法用于验证链路。
不做：任何业务方法（举报、审核、下架等一律留到阶段 3）。

### 规格依据
- OPS §3.1 —— 鉴权以操作提交时的最新账号状态与权限为准，不依赖进入页面时的结果
- OPS §13 —— 审计日志 9 个必含字段，覆盖 10 类事件；不得记录密码等凭证与可继续使用的下载地址
- D-072 —— 后台不脱敏、不设二次验证、导出不受限制；对应的代价是全量审计
- OPS §12.2 —— 错误态分类；重复提交返回首次结果或当前最终状态
- DATA_MODEL §10.8 —— grouporder-oplog 表结构

### 形态参照
无界面。

### 复用与代码参照
- 云对象写法参照 uniCloud 官方 importObject 规范
- 鉴权可复用 uni-id-common 的 checkToken，但**角色与权限点校验需自行实现**

### 已知陷阱
- ADM-30：`uni-config-center` 的 `uni-id/config.json` 仍为模板默认值，生产前必须替换 `tokenSecret`。
- ADM-10：自定义权限点只控菜单可见性，不控数据访问；云对象内必须自行校验权限点。
```

## 反面清单（这样投喂会出问题）

| ❌ 做法 | 后果 |
|---|---|
| 「先把 docs 目录全读一遍，然后写 A-08」 | 5000+ 行淹没重点，关键约束被忽略；Token 消耗大且注意力分散 |
| 「按效果图把 17 屏都实现了」 | 范围过大，基础设施缺失导致每页重复实现鉴权与审计，最终不一致 |
| 只给效果图不给规格 | 图只表达形态，权限规则、状态机、幂等要求都在文档里 |
| 只给规格不给效果图 | 会自造一套 UI，重演本项目 v1 的教训（自建框架而非复用 uni-admin） |
| 不点名 ADM 陷阱 | 与本任务相关的通常 2～4 条，不点名容易遗漏 |
| 不给验收标准 | 无法判断完成度，返工率高 |
| 允许 Agent 自行裁决规格矛盾 | 产生第二个事实源，与项目既定规则冲突 |
