#### M-29 的三个入口

M-29 商品库管理页可从三处进入，三处都要做：

1. 「我的」（M-08）→「我的商品库」。账号级常规入口。
2. **创建/编辑活动页（M-10）商品列表区块，标题行右侧的文字链接「管理商品库 ›」。**
3. M-28 历史商品选择页右上角的「管理」。挑商品时发现某条模板信息过时，就地跳过去改。

**入口 2 必须是轻量文字链接，不能做成第四个并列按钮。** 「＋ 添加商品」「↺ 复用历史商品」「↺ 复用历史接龙」是三个主操作；再并排一个「我的商品库」，团长会分不清它和「复用历史商品」的区别——两者字面都指向商品库，但一个往活动里加商品、一个不加。降低视觉层级是消除歧义最省事的办法。

配套行为：

- 入口 2 用 `navigateTo`，返回时 M-10 仍在页面栈中，**草稿表单状态不得丢失**。
- 在 M-29 中编辑或删除库记录，**不影响已加入当前活动的商品**（复制语义的直接推论，见 GOODS_LIB_SPEC §2.3）。
- 从 M-29 返回 M-28 时，M-28 列表需刷新以反映刚才的编辑或删除。

## 4. 六条红线

这六处是本轮最容易做错的地方，每一条都有明确的错误后果。

### ① 推荐商品不置顶

`is_recommend` **不进入任何排序表达式**。排序恒为 `sort ASC, create_date ASC`。推荐只表现为角标与边框高亮，商品在列表中的位置不变。

「推荐」这个词天然带着「该最显眼」的暗示，实现时极易顺手加个置顶。但置顶一旦启用，商品管理页就必须分「推荐/其他」两区并禁止跨区拖拽，否则会出现「把商品拖到最顶部、`sort` 变成 1，却仍显示在推荐之后」——拖了没反应，是最难向用户解释的一类 bug。产品负责人已明确**暂不实施置顶**。在他再次明确要求前不要自行加上。

### ② 分类只做筛选

M-28 的分类 chips 点击后过滤列表，商品仍逐个勾选。**不做「按分类批量加入」**，不加「全选本分类」按钮。整组重复的场景由 D-067 复用历史接龙覆盖，两条路径都做会造成功能重叠。

### ③ 两条绕过治理的路径必须一起堵

违规商品有两个入口可以进新活动，只堵一条等于没堵：

- **商品库**：运营下架商品时反查并封禁库记录（GOODS_LIB_SPEC §7，两条匹配取并集）
- **复制活动**：源活动中已下架的商品剔除并明确告知；已下架的活动整个不可作为源（`DATA_MODEL` §4.10「四条实现约束」1、2）

### ④ 复制活动的截止时间要预填，不能留空

```
新 end_time = 当前时间 + (源活动 end_time − publish_date)
```

`publish_date` 为空时改用 `create_date`；结果 ≤ 0 或字段缺失兜底 3 天。预填值必须在页面显眼展示且可直接修改，**不得折叠隐藏**——藏起来就退化成盲目默认值了。

### ⑤ 逐项确认只做一套

商品库复用与活动复制，两者的价格/库存/限购确认必须复用 `GOODS_LIB_SPEC` §5.3 的同一套机制与组件。出现两套确认流程说明拆分错了，回来重新对齐。

### ⑥ `lib_id` 只用于治理定位

禁止通过 `lib_id` 联表读取库记录内容来展示活动商品，禁止任何方向的字段同步，禁止声明为 `foreignKey`，禁止因库记录软删而清空。见 GOODS_LIB_SPEC §2.2、§2.3。

看到一个 id 字段就想 JOIN 是本能，但一旦联了，「复制不是引用」就破了，历史快照、治理隔离、留存期三套设计会跟着一起塌。
