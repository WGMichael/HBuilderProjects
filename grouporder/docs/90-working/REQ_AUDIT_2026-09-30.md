## 2. 执行摘要

**整体判断**：文档体系本身相当一致。真正互相矛盾的功能点只有 7 处，其中 1 处高严重度。主要风险在两类空白：规则没有写完的功能点 146 处（38 处高严重度），以及文档与实现的偏离 83 处（2 处严重、30 处高）。仍成立的问题共 261 个，其中 219 个在现有的 OPEN_ISSUES 等清单里没有登记。

**最先要处理的九件事**：

1. 内容审核默认按自动模式，而内容检测恒返回通过，文字内容不经检查就上线（I-01）。这是提审最先被问到的点。
2. 已注销账号的三年期订单，「限制处理」与 D-072 的「不限制访问」互相矛盾（C-01）；注销入口还绕过 D-056 的前置校验（I-05）。
3. 进行中的活动改内容后重审，状态迁移、订单去向、撤回与驳回后的去向、到期处理都没有定义（U-01）。
4. 发布主流程走不通：发起页每次显示都清空草稿（I-02），封面图必填却没有上传入口（I-12）。
5. 改单时未改动的明细按当前价重算，与价格快照规则冲突（I-03）；限购与库存校验先查后写，并发可突破限购（I-09）。
6. 治理下架后的行为边界没有规定：游客可见性、团长可用操作、清单导出、申诉通道（U-29、U-30、U-04）。
7. 举报处理与复核缺规格：领取后释放、复核效力、违规类型、恢复条件（U-22、U-11、U-08、U-23）。
8. 导出与明细读取硬编码了上限，超出部分静默丢弃，文档也没有订单数与明细数的上限（I-04）。
9. 三年到期匿名化没有处理订单上的 user_id（I-08），运营导出文件没有保留期与清理规则（U-10）。

**问题集中的主题**（仍成立的问题数）：活动生命周期 32、隐私与数据留存 27、举报与治理 25、商品库与复用 24、订单与库存 20、后台查询与统计 20。

## 3. 需要产品负责人拍板的决策包

### 决策 1：进行中的活动被改内容后如何重审

- 问题：进行中且已有订单的活动，团长改了文字或图片（D-048）后怎么处理？现状：代码把它直接改成「审核中」，状态机文档里没有这条迁移；重审被驳回或撤回后退回草稿，带着订单却对参与者不可见，也不被自动截止扫描。
- 选项：
  - A：线上继续展示并接受订单的旧版本，新版本另行审核，通过后替换。活动状态不变、不暂停接龙，需要同时保存两份内容。
  - B：活动整体退回「审核中」并暂停接龙；驳回或撤回后回到「进行中」，内容还原为上次通过的版本。需要保存上次通过的内容快照，审核期间已下单参与者只读，可缩减和取消。
  - C：维持字面口径（退回审核中，驳回或撤回退回草稿），只补规则：草稿态订单对参与者可见可取消、自动截止要扫描草稿、到期直接关闭。工程量最小，但「带订单的草稿」会长期存在。
- 推荐：推荐 B。它同时满足 D-048「审核通过后才重新开放」和 D-079「审核中冻结」，避免双版本并存。同时要写明：审核期间自动截止照常生效；自动审核模式下重审按新提交处理。
- 相关发现：U-01、U-06

### 决策 2：已注销账号的订单：运营后台能看多少

- 问题：D-035、PRD 5.7、OPS 16 规定注销后三年期内的订单转为「限制处理」，只用于争议、审计和必要合规；晚出的 D-072 规定运营后台完全不脱敏、不限制访问，且没有为限制处理订单设例外。代码按 D-072 全量返回，限制处理标志只被写入、从未被读取。
- 选项：
  - A：以 D-072 为准，一视同仁全部展示；PRD 与 OPS 里的「限制处理」改成只约束小程序端与统计口径。
  - B：已注销账号的订单默认隐藏姓名、电话、地址，仅在关联的隐私事项（A-16）内可查看，并留审计。
- 推荐：推荐 B。范围只是已注销账号的三年期内订单，符合 D-035 和提审隐私条目，代价是 A-16 增加事项内查看入口。若选 A，必须同步删掉 PRD 与 OPS 的限制处理表述，并在提审自查中说明理由。
- 相关发现：C-01、I-28

### 决策 3：账号注销走哪条路径，到期匿名化匿名什么

- 问题：现状：小程序「注销账号」直接进入官方注销页，绕过 D-056 的前置校验（有进行中活动或有效订单不得注销）和隐私事项登记；用户提交的事项没有任何执行环节，定时任务只推进运营创建的事项；三年到期匿名化没有处理订单上的 user_id，仍可反查到账号。
- 选项：
  - A：用户自助注销。服务端先做 D-056 校验并列出阻塞对象，通过后系统自动执行账号资料与地址簿的删除或匿名化，运营 A-16 只读跟踪。
  - B：用户只提交申请，由运营核验身份后手动触发执行。需要另外定义身份核验标准与时限。
- 推荐：推荐 A。运营后台已不提供业务数据删除入口，B 会让「谁来执行」无解。落地要点：把注销入口改接隐私事项提交接口；补一份匿名化对象清单（含订单与明细的 user_id、自提联系人）；未到期时用户请求删除一律拒绝并告知到期时间。
- 相关发现：I-05、U-35、U-36、I-08、U-25、U-26

### 决策 4：内容审核的默认值与检测降级

- 问题：配置缺失、检测接口异常、或用户没有 openid 时，活动怎么审核？现状：默认按自动审核，而内容检测恒返回通过，文字内容不经任何检查就上线，与 D-022、负面清单和提审自查冲突。
- 选项：
  - A：一律进入人工审核队列，不自动放行；检测服务未接入前不得把审核模式切到自动。
  - B：保持自动审核，检测异常时按通过放行，只依赖举报与事后下架。
- 推荐：推荐 A。首版没有发布者资质审核，「自动加恒通过」等于不审，这是提审最先被问到的点。需要资质的商品一并明确为一律禁止。
- 相关发现：I-01、U-31、U-37

### 决策 5：治理下架之后的行为边界

- 问题：活动或商品被平台下架后：游客与已下单参与者还能不能看到内容；团长能否继续截止、取消、调库存、导出清单；参与者能否缩减或取消订单；已截止或已取消的活动被下架后能否恢复；整个活动下架时库记录是否一并封禁。文档只在矩阵里写了一部分，代码各处做法不一。
- 选项：
  - A：履约优先。只禁止新增与扩大，已有订单和清单照常可用，内容仍可见，顶部标注「已下架」。
  - B：冻结优先。团长的经营动作一并冻结，直到运营恢复。
  - C：折中。对游客与新访问者隐藏内容，只显示「已被平台下架」；已下单参与者仍可看自己的订单快照；团长仍可导出清单履约，但不能新增或扩大。
- 推荐：推荐 C。线下交付已经发生的订单需要能履约，同时避免违规内容继续展示。库记录只封禁运营在下架时点名的商品，对应 D-064 的精确匹配，不连带整个活动。
- 相关发现：U-29、U-30、U-04、U-21、U-19

### 决策 6：举报处理与复核链路补规格

- 问题：举报链路缺一批规则：领取后不处理怎么办；复核由谁发起、结论与原结论不同如何生效；违规类型有哪些；恢复需要什么结论；发布限制之间如何迁移；游客能否举报；D-082 结案自动处置时若举报没有指向商品怎么办、失败如何回滚。
- 选项：
  - A：按最小规则补齐。违规类型取负面清单类目加「其他」；领取超过一定时限自动释放，且任一运营可接手；复核结论只记录，恢复必须由运营手动并关联复核记录；举报须登录；选「下架商品」而举报无商品时拒绝并要求先选商品。
  - B：保持现状，只在文档标注「首版不定义」，靠运营内部约定。
- 推荐：推荐 A。这些分支运营每天都会碰到，代码里已经各自做了隐含选择（例如只有领取人能结案），不写下来等于让实现替产品做决定。
- 相关发现：U-02、U-07、U-22、U-11、U-08、U-23、I-19、U-12、U-09、U-17

### 决策 7：改单计价与限购并发

- 问题：团长改价后，参与者修改旧订单如何计价？现状：改单时未改动的明细也按当前价重取快照，与 D-018「已提交订单按价格快照保留」冲突。另外限购与库存校验先查后写、非原子，并发可突破每人限购；改单没有版本闸门，订单号冲突不重试。
- 选项：
  - A：已有明细保留原价，新增商品和已有商品加量的部分用当前价；限购必须在并发下也不超限，增加按用户和商品的原子计数。
  - B：整张订单按改单时的当前价重算；首版允许并发下极小概率超限，PRD 5.3 改成仅库存由服务端原子保证。
- 推荐：推荐 A。与 D-018 一致，参与者不会因团长改价被动多付；限购涉及公平和纠纷，建议保证原子性。
- 相关发现：I-03、I-09、I-24、I-18、U-27、I-17

### 决策 8：容量与上限：订单数、商品数、导出

- 问题：文档没有给出单用户在一个活动里的订单数上限，D-024 只有 500 人、50 商品的容量估算，PRD 还写明不作为界面硬限制；代码却把 50 商品做成硬拒绝，导出硬编码只读 600 单、2000 行，订单明细查询固定 500 条，超出部分静默丢弃。
- 选项：
  - A：把上限写进产品。每人每活动最多 N 张订单（需给出数字），50 商品作为硬上限并在发起页提示；导出与查询必须取全量，超出单次读取上限时分批。
  - B：不设产品上限，容量仅作设计估算；代码取消硬拦截，导出与查询全部分页取全量。
- 推荐：推荐 A，并把 N 定下来。无论选哪个，都不允许静默截断：要么分批取全，要么明确报错。
- 相关发现：I-04、U-20、I-26、C-05

### 决策 9：活动取消后的订单与统计口径

- 问题：D-052 规定已取消活动显示取消前的统计快照、不计入当前有效统计，但没有规定快照存在哪里、订单状态是否改变。现状：已取消活动的订单仍计入团长的有效汇总。
- 选项：
  - A：订单与明细状态保持不变，统计和清单一律按「活动已取消」排除，历史页显示取消时固化的快照（新增快照字段）。
  - B：取消时把全部有效订单置为「已取消」并返还库存，历史页直接聚合。
- 推荐：推荐 A。保留订单原状态便于追溯，也避免取消时的批量写；需要补快照字段，并让后台统计排除已取消活动。
- 相关发现：U-03、I-16

### 决策 10：清单导出规则

- 问题：小程序端如何拿到 Excel；重复点「生成」是否产生新版本；同一商品出现多个价格或单位时汇总怎么显示。现状：只能复制 30 分钟链接（微信内打不开 xlsx），版本号语义不统一，汇总单价口径不一。
- 选项：
  - 交付方式 A：应用内 downloadFile 加 openDocument，不出现链接，需配置云存储下载域名。B：复制链接到浏览器打开，接受被转发的风险。
  - 版本 A：复用已有文件，仅订单作废后才产生新版本。B：每次点击都生成新文件与新版本。
  - 汇总 A：按「价格加单位」拆成多行。B：只显示当前价并备注含历史价。C：汇总不显示单价，只显示份数与预计金额。
- 推荐：推荐交付 A、版本 A、汇总 A。前两项能直接消除链接外泄面，第三项让清单与改价历史保持一致。
- 相关发现：U-34、U-28、U-20

### 决策 11：账号绑定、找回密码与游客态

- 问题：绑定时哪个账号存活；「已有业务数据」按什么口径判定；登录页的「微信验证重设密码」入口如何处理；申诉时以什么核验；游客打开接龙 tab 应看到什么。现状：小程序还缺自助发起绑定的入口，游客进接龙 tab 被强制跳登录。
- 选项：
  - 绑定 A：只允许把微信身份绑到「有数据的账号」上，空账号作废；反向一律拒绝，提示为微信账号补设用户名密码。B：仅双方都无数据时才允许任意方向绑定。
