## 4. 三 tab 大厅的四个硬约束（D-061 的直接后果）

这一节是 client 端**最容易做错**的地方，四条都来自微信小程序对 tabBar 的平台限制。

1. **中间「发起接龙」是凸起入口，必须自定义 tabBar 组件实现。** 微信原生 tabBar 做不出凸起效果。
2. **tabBar 页只能用 `switchTab` 进入，且不可带参数。** 这是平台约束，不是设计选择。
3. **因此「发起接龙」tab 恒为新建态。** 编辑草稿**必须是另一个非 tabBar 页面**——从 M-09 打开草稿时用 `navigateTo` 进入该页，不要试图给 tab 传 `activity_id`。
4. **接龙 tab 含三个子页**（待办事项 / 我发起的 / 我参与的），**默认子页是待办事项**（M-27）。子页切换在 tab 内部完成，不是三个独立 tabBar 项。

**另外两条与入口有关：**

- **M-10 有三个并列主按钮**：「＋ 添加商品」「↺ 复用历史商品」「↺ 复用历史接龙」。商品列表区块标题行右侧再加一个**轻量文字链接**「管理商品库 ›」——**不能做成第四个并列按钮**，否则团长分不清它和「复用历史商品」（一个往活动里加商品、一个不加）。
- **M-29 商品库管理有三个入口**：M-08「我的商品库」、M-10 的文字链接、M-28 右上角「管理」。入口 2 用 `navigateTo`，返回时 M-10 仍在页面栈中，**草稿表单状态不得丢失**；从 M-29 返回 M-28 时 M-28 需刷新。

## 5. 登录与账号（D-029 ～ D-034）

| 规则 | 要点 |
|---|---|
| 双登录 | 微信授权 + 用户名密码，两者进入**同一平台用户**；平台注册账号可绑定微信，绑定后可用微信找回密码 |
| **不采集手机号** | 账号体系**不关联手机号**（D-029）。手机号只存在于收货信息里。登录页不要出现短信验证码，`loginTypes` 里不要留 `smsCode` |
| 一对一绑定 | 一个微信只能绑一个平台账号，反之亦然（D-030）。双方都已有业务数据时**不受理申诉、不合并、不迁移**（D-055），M-07 展示明确结论 |
| 未登录可浏览 | 允许未登录浏览活动非敏感内容，**提交时才要求登录**（D-033）。登录后要能回到原来的位置继续 |
| 分享入口 | 持有效入口的微信用户均可进入（D-034），敏感数据仍受权限控制。活动**不进入任何公开列表**（D-059） |

## 6. 八条不能违反的规则

前六条是 `update.md §4` 的既有红线，后两条是小程序端特有。

1. **推荐商品不置顶。** `is_recommend` **不进入任何排序表达式**，排序恒为 `sort ASC, create_date ASC`。推荐只表现为角标与边框高亮，位置不变（D-065）。
2. **分类只做筛选。** M-28 的分类 chips 点击后过滤列表，商品仍逐个勾选。**不做「按分类批量加入」**、不加「全选本分类」（D-066）。
3. **两条绕过治理的路径必须一起堵。** 商品库侧：被下架商品的库记录封禁不可复用；复制活动侧：源活动中已下架的商品剔除并告知，已下架的活动整个不可作为源。只堵一条等于没堵。
4. **复制活动的截止时间要预填，不能留空。** `新 end_time = 当前时间 + (源活动 end_time − publish_date)`，`publish_date` 为空用 `create_date`，结果 ≤ 0 或缺字段兜底 3 天。预填值**必须显眼展示且可直接修改，不得折叠隐藏**（D-067）。
5. **逐项确认只做一套。** 商品库复用与活动复制的价格/库存/限购确认，**必须复用同一套机制与组件**（`GOODS_LIB_SPEC §5.3`）。出现两套说明拆分错了。
6. **`lib_id` 只用于治理定位。** 禁止通过它联表读库记录来展示活动商品、禁止任何方向的字段同步、禁止声明 `foreignKey`、禁止因库记录软删而清空。「复制不是引用」一旦破了，历史快照、治理隔离、留存期三套设计会跟着塌。
7. **业务状态与治理状态是两个独立字段，不得合并成一个标签。** 活动可以同时是「进行中 + 已下架」。团长主动停售与平台治理下架也不是同一状态。
8. **统计只用白名单指标**：已购买份数、有效总份数、有效订单数、预计金额。**不得出现**销售额、实收金额、实际成交、GMV——平台不收款，用这些词是对事实的错误陈述。

**还有四条「不要退回去」**：不做公开活动列表与任何发现/推荐/搜索/分类入口（D-059）；待办可由用户「关闭」并把已读状态落库（**D-062**，走 `grouporder-todo-dismiss` 表 + `todoDismiss` 方法），条目本身仍是派生视图、处理完毕后自然消退——**注意这与运营后台不同**：D-070 规定的「不提供关闭或忽略」只针对后台工作台，且 D-070 原文明确对比「不需要小程序端 `grouporder-todo-dismiss` 那样的已读状态表」，切勿把后台规则套到小程序端；自提活动**不采集完整地址**（D-060）；首版**无订阅消息**（D-032），站内触达全部落在 M-27 待办上。

## 7. 已知陷阱

| # | 陷阱 |
|---|---|
| 1 | **`uni-id-pages` 模块升级会覆盖 `config.js`。** 裁剪 `loginTypes` 的改动在升级后会被还原，升级后必须重新核对（`DATA_MODEL §3` 三项必检） |
| 2 | **同一用户同一活动可有多张有效订单**（D-025）。「再下一单」是创建新订单，不是修改或恢复原订单。每人限购按**同一用户对同一商品的累计有效份数**校验，按商品分别计算 |
| 3 | **收货信息与订单收货快照分离。** 下单时复制一份快照；之后用户改地址簿或删记录，**不影响历史订单** |
| 4 | **`total_stock = 0` 表示不设上限，不是售罄**；`per_user_limit = 0` 表示不限购。只有正整数才参与服务端原子校验（D-044） |
| 5 | **写操作「结果未知」时先锁定重复动作再查询结果**，确认失败后才允许重发。同一下单意图的重复点击或网络重试必须复用原结果，不新增订单 |
| 6 | **截止以服务端时间为准**，本地倒计时只用于展示，不得据此放行提交 |
| 7 | **自提与送货上门的订单表单不同**：自提只要收货人姓名与电话，**不进地址簿选择流程**；送货上门才强制选完整地址（D-060）。交付方式发布后不可改 |
| 8 | **全部商品停售或售罄时活动仍是「进行中」**，页面显示暂无可购买商品，团长仍可新增商品、补库存、恢复售卖或提前截止 |

## 9. 工作方式

1. **先给实施方案**（改动哪些文件、关键逻辑、风险点），确认后再写代码
2. 只改 `grouporder-client/src/` 下的 `pages/**`、`components/**`、`pages.json`、`manifest.json`、`uni_modules/uni-id-pages/config.js`
3. **不改** `cloudfunctions/**`、`uniCloud-alipay/database/**`、`docs/**`、`CLOUD_API.md`、`grouporder-admin/**`
4. 发现规格矛盾、效果图与文档对不上、或接口缺方法 —— **写在回复里上报，不自行裁决**
5. 写完自我 review：空值风险、生命周期、命名、项目规范
