## 1. 需求 ①：推荐标识

### 1.1 先澄清一个歧义

「推荐」有两种完全不同的语义，方案和风险差别很大：

| 语义 | 含义 | 风险 |
|---|---|---|
| **A. 团长自荐**（推测你指这个） | 团长在自己的活动里标注主推商品，参与者看到角标，更容易注意到 | 无。属于活动内的排版强调 |
| **B. 平台推荐** | 运营给某些商品打推荐标，在平台层面做流量倾斜 | **显著**。平台参与商品推荐与流量分配，是「电商平台」类目的典型特征，会直接抵消刚刚废止公开活动列表（D-059）换来的合规收益 |

**已确认采用 A 团长自荐。** 平台不参与任何商品推荐或流量分配，D-059 的合规论证不受影响。这一条要写进决策记录——它不只是交互选择，也是产品形态的边界声明。

### 1.2 方案

两张表各加一个字段，语义不同：

| 表 | 字段 | 含义 |
|---|---|---|
| `grouporder-goods-lib` | `is_recommend` int 0/1 默认 0 | **默认值**。表示团长习惯性主推该商品，复用时带入活动 |
| `grouporder-goods` | `is_recommend` int 0/1 默认 0 | **本次活动生效值**。参与者看到的就是它 |

流转规则，与 `last_price` 等三个经营字段完全一致：

- 沉淀时：`lib.is_recommend = goods.is_recommend`
- 复用时：`goods.is_recommend = lib.is_recommend`（预填）
- 活动内修改 `goods.is_recommend`：**不回写 lib**，符合快照原则
- 在 M-29 商品库管理中可直接修改 lib 的默认值

### 1.3 两个细节（已定）

**① 推荐商品置顶。**（2026-09-15 修订，推翻此前「只做视觉角标」的结论）

统一排序规则，活动详情页与团长商品管理页**使用同一条**：

```
ORDER BY is_recommend DESC, sort ASC, create_date ASC
```

- `is_recommend DESC`：推荐商品排在最前。
- `sort ASC`：团长拖拽产生的顺序。
- `create_date ASC`：**必须保留的兜底键**。同 `sort` 值时若无次级排序，数据库返回顺序不稳定，分页会出现重复或遗漏。

关于「没有 `sort` 就按数据顺序」：`sort` 的 `defaultValue` 为 0，而 `GOODS_LIB_SPEC` §5.2 已规定新增商品时 `sort` 取当前活动最大值 +1，因此 `sort` 在正常路径下永远有有效值，兜底键只在异常数据时生效。**不需要把 `sort` 改为可空**。

**拖拽必须限制在同区内。** 若允许跨区拖拽，团长把一个非推荐商品拖到列表最顶部、它的 `sort` 变成 1，但因 `is_recommend DESC` 优先级更高，它仍然显示在推荐商品之后——拖了没反应，是最难解释的一类 bug。因此：

- 管理页把列表分为「推荐」与「其他」两个区块，各自可拖拽排序，不能跨区拖动。
- 改变推荐状态在商品编辑页操作，不通过拖拽完成。
- 拖拽提交时服务端按拖拽后的可视顺序整体重写该活动全部商品的 `sort`（从 1 连续递增），不允许出现部分有值、部分为默认值的混合状态。

**Excel 清单的商品汇总（D-053）建议采用同一排序**，使团长在小程序里看到的顺序与打印出来的配货单一致。

**索引**：`grouporder-goods.index.json` 的 `activity_gov_sort` 建议改为 `activity_id + governance_status + is_recommend + sort`。schema 尚未上传服务空间，此刻修改代价为零；即便不改，单活动上限 50 件商品的内存排序也无实际影响。

**② 每个活动最多 5 个推荐。** 50 个商品全标推荐，标识等于没有。超出时提示先取消其他推荐。上限在服务端校验，不只做前端限制。

## 2. 需求 ②：商品库分组

### 2.1 方案选型

| 方案 | 做法 | 评价 |
|---|---|---|
| **A. 独立分类表**（推荐） | 新建 `grouporder-goods-category`，lib 加 `category_id` | 分类可重命名、排序、删除；改一次全局生效 |
| B. lib 存分类名字符串 | lib 加 `category` 文本字段，前端聚合 | 0 新表，但重命名要批量更新全部记录，且必然出现「蔬菜」与「蔬菜 」两个分类 |
| C. 多标签数组 | lib 加 `tags` 数组 | 对「选择哪些分类的商品」这个场景是过度设计，且筛选时会出现同一商品被多次选中的歧义 |

采用 **A**。

### 2.2 新表 `grouporder-goods-category`

| 字段 | bsonType | 必填 | 说明 |
|---|---|---|---|
| `_id` | objectId | - | |
| `user_id` | string | ✓ | 归属用户，分类为用户私有 |
| `name` | string | ✓ | 1–10 字 |
| `sort` | int | ✓ | 用户自定义顺序，默认 0 |
| `create_date` | timestamp | ✓ | |

`grouporder-goods-lib` 增加 `category_id`（string，可空）。

索引：`user_id + sort`。

### 2.3 五个必须定清楚的设计点

**① 一个商品只属于一个分组。** 采用一对多而非多对多。理由：符合「分类」的直觉；且多对多会让「按分类选择商品」出现同一商品被重复选中的歧义，前端要额外去重。

**② 不建「未分组」实体。** `category_id` 为空即视为未分组，不为每个用户初始化一条默认分类记录。M-28 的筛选条中「未分组」是一个查询条件，不是一条数据。

**③ 删除分类不删商品。** 删除分类时把该分类下所有 lib 记录的 `category_id` 置空（归入未分组），分类记录本身可硬删——它不是业务记录，不进入任何订单或清单，无需软删和留痕。

**④ `grouporder-goods` 不需要分类字段。** 按 `GOODS_LIB_SPEC` §2.3 的判据：凡是会进入订单、清单、履约凭证的内容才存快照。分类是「我的商品库的组织方式」，是团长的私人抽屉，不进入活动展示、不进入 Excel 清单、参与者永远看不到。因此活动商品无需携带。

> 例外情形：若将来希望 Excel 清单按分类分组打印（如配货时按「蔬菜/蛋奶」分堆），那时需要的是**活动级的商品分组**，与 lib 的私人分类是两个东西，不应混用。首版不做。

**⑤ 分类名不需要内容安全检测。** 分类只有用户自己可见，不对外展示、不进入任何分享内容，无需送 `msgSecCheck`，省一笔接口调用。这一条要写进文档，否则实现时会出于保险默认送检。

### 2.4 分类交互：只做筛选（已定）

M-28 顶部加一行分类 chips（全部 / 蔬菜 / 蛋奶 / … / 未分组），点击过滤列表，商品仍然逐个勾选。

**不做「按分类批量加入」。** 「每周三蔬菜团」这类整组重复的场景，由需求 ③ 复用历史接龙覆盖，一步到位，比批量加入更彻底；两条路径都做会造成功能重叠。分类在此只承担"找得到"的职责，不承担"批量组装"。

## 3. 需求 ③：复用历史接龙

### 3.1 它就是 P1-08

`DECISIONS.md` §5 的 P1-08「是否支持复制历史活动？」当前结论是「放入后续迭代」。本需求等于把它提前，实施时应同步把 P1-08 改为已确认并补一条决策编号。

### 3.2 复制什么、不复制什么

| 对象 | 处理 |
|---|---|
| `title` | 复制，用户可改（建议不自动加「副本」后缀，团长通常要改成「9月24日蔬菜团」这类新名字） |
| `description` / `cover_image` / `images` | 复制 |
| `delivery_type`（交付方式） | 复制 |
| `end_time` 截止时间 | **不复制，必须重填**。旧活动的截止时间必然已过期 |
| 活动状态 | 一律置为**草稿** |
| 商品内容（名称/图片/说明/单位） | 复制 |
| 商品的 `price` / `total_stock` / `per_user_limit` | 复制为预填值，**仍须逐项确认**（复用 §5.3 的既有机制） |
| 商品的 `lib_id` | **复制**。来源仍是同一条库记录，治理反写链路必须保持连通 |
| 商品的 `sold_qty` / `ever_ordered` / `governance_status` / `on_sale` | 全部初始化 |
| 订单 / 订单明细 | **绝不复制** |
| 举报记录 / 治理状态 / 审核记录 | 不复制 |

### 3.3 五个坑

**① 被治理下架的商品必须排除。** 源活动里若有 `governance_status = 1` 的商品，复制时必须跳过并明确告知用户「其中 1 件商品因违规已被下架，未包含在本次复制中」。

不处理的话，这是一条与 `GOODS_LIB_SPEC` §7 同类的**绕过治理路径**：违规商品在商品库被封禁了，但通过复制旧活动照样能带进新活动。两个入口都要堵。

**② 被平台下架的整个活动不可复制。** 源活动 `governance_status = 1` 时拒绝复制并说明原因。团长自己取消的活动（`已取消`）可以复制——那是经营决定，不是违规。

**③ 截止时间不能有默认值。** 必须让用户显式填写，不能预填「上次的时间」或「7 天后」。预填会导致团长闭眼下一步，发出一个截止时间莫名其妙的活动。

**④ 不重复触发沉淀。** 复制活动时不应再往商品库沉淀（源商品当初保存时已沉淀过），否则会刷乱 `last_used_time` 的排序。`use_count` 同样**不递增**——这不是「从库复用」。

**⑤ 复制出的活动仍要走发布审核（D-043）。** 它是一个全新活动，不因内容与旧活动相同而免审。

### 3.4 入口与页面

- 主入口：M-10 发起接龙页，与「添加商品」「复用历史商品」并列第三个按钮 **「↺ 复用历史接龙」**
- 辅入口：「我发起的」列表每项的「再来一次」
- 新页：**M-31 历史接龙选择**，倒序列出，显示标题、截止日期、商品数、订单数

**可作为源的活动范围（已定）**：已截止、已取消、**进行中**。

- 包含进行中：真实场景是本周的团还在跑，团长提前把下周的排好。此时 UI 必须明确提示「将创建一个新的草稿，不影响当前正在进行的活动」，否则团长会误以为是在编辑当前活动。
- 不包含草稿：草稿本来就能直接打开编辑，复制它没有意义。
- 被平台下架（`governance_status = 1`）的活动一律不可作为源，无论业务状态为何。

| 文件 | 改动 |
|---|---|
| schema | **不改**。`activity` 与 `goods` 都不需要新字段 |
| `DECISIONS.md` | P1-08 转为已确认；新增一条决策明确复制范围与治理排除规则 |

### 3.6 关于 `source_activity_id`

按 `lib_id` 的同一标准评估后：**不加**。

`lib_id` 存在的唯一理由是治理反写需要精确定位库记录。而复制出的活动，其商品已各自携带 `lib_id`，治理链路完整；源活动被下架也不应连坐副本（内容是快照，且违规商品已在复制时排除）。既无治理必要性，就不加——来源追溯本身不构成加字段的理由，否则这个标准会被逐步稀释。

## 4. 三项之间的交叉影响

**需求 ③ 会削弱需求 ② 的价值，但不能互相替代。** 两者服务的是不同场景：

| 场景 | 更合适的功能 |
|---|---|
| 每周三蔬菜团，商品几乎不变 | ③ 复用历史接龙，一步到位 |
| 这次做水果专场、下次做蛋奶专场，每次组合不同 | ② 商品库分组 + 批量加入 |

因此对**定期团团长**，③ 的实际价值大于 ②，尽管工作量也更大。

**需求 ① 与 ②③ 完全正交**，任何顺序都不冲突。

**②③ 共用一处逻辑**：③ 的商品逐项确认应直接复用 §5.3 的既有机制与组件，不要另做一套。实现时若出现两套确认流程，说明拆分错了。

## 5. 实施顺序（已定）

**第一步：①② 的 schema 合并为一次变更。** 一次性加完 `goods-lib.is_recommend`、`goods.is_recommend`、`goods-lib.category_id`，并新建 `grouporder-goods-category` 表，一次上传服务空间，避免连续两次变更。

**第二步：功能仍分开实现。** schema 合并不等于功能合并——① 推荐标识约半天即可完成并验收，② 分组的页面与接口可随后推进，互不阻塞。

**第三步：③ 复用历史接龙。** 它不改任何 schema，因此不受前两项的 schema 节奏约束，可与 ② 并行开发。

注意 ③ 的商品逐项确认必须复用 `GOODS_LIB_SPEC` §5.3 的既有机制与组件。实现中若出现第二套确认流程，说明拆分错了，回来重新对齐。
