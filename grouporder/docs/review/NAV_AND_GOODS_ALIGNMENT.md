## 2. 冲突清单与方案

### C-01　导航结构：首页职责与三 tab 大厅冲突

**现状**：`UX_FLOW_SPEC` §3.1 的 M-01 首页 =「发起接龙 + 公开且进行中的活动 + 使用说明」，且是底部导航项；M-09「我发起的」与 M-18「我参与的」是独立页面，入口写的是 M-01、M-08。

**冲突**：目标结构里不存在"首页"这个页面——大厅本身就是 tabBar 容器，三个 tab 各自是一个页面。

**方案**：

```
大厅（tabBar 容器，无独立页面内容）
├── T1 接龙        → 顶部三子 tab
│     ├── 待办事项   （新增，见 C-03）
│     ├── 我发起的   （原 M-09，页面编号保留，入口改为 tab 切换）
│     └── 我参与的   （原 M-18，同上）
├── T2 发起接龙    → 原 M-10 创建活动（作为 tabBar 页，见 C-07 的约束）
└── T3 我的        → 原 M-08 个人与设置（增设团长工具分组，见 C-05）
```

- 删除 M-01「首页」，同时删除"使用说明"的独立入口（挪进 T3「我的」）。
- M-09、M-18 保留原页面编号与职责描述，只改「主要入口」列：由 `M-01、M-08` 改为 `接龙 tab 子页`。
- 新增 M-27「待办事项」、M-28「历史商品选择」。

**影响文件**：`UX_FLOW_SPEC` §3.1 页面表、§4 各流程的"入口"字段（F-M03、F-M04、F-M06 均引用了 M-01）、`PRD` §6 页面表。

### C-03　待办事项：全新概念，文档零覆盖

**现状**：「待办」在项目里只出现在运营后台 A-03 工作台，小程序端没有任何相关定义。

**这一项同时解决了上一轮评审的 H-06**：首版不做订阅消息（D-032），导致活动被取消/下架、举报结果、审核不通过等事件对用户完全没有触达手段。待办 tab 就是站内触达的载体。

**首版待办事项定义**：

| 优先级 | 事项 | 面向 | 触发条件 | 消退条件 |
|---|---|---|---|---|
| 1 | 活动被治理下架 | 团长 | 活动或其商品 `governance_status = 1`（含 D-058 图片回调命中） | 用户点击查看后关闭 |
| 1 | 发布审核不通过 | 团长 | 活动退回草稿且带不通过原因 | 重新提交或删除草稿 |
| 2 | 我参与的活动被取消或下架 | 参与者 | 本人有有效订单的活动转为已取消 / 已下架 | 用户点击查看后关闭 |
| 2 | 活动已截止，待生成清单 | 团长 | 活动已截止且从未成功生成过清单 | 成功生成一次清单 |
| 3 | 我发起的活动 24 小时内截止 | 团长 | 进行中且 `end_time - now < 24h` | 活动截止 |
| 3 | 我参与的活动 24 小时内截止 | 参与者 | 同上且本人有有效订单 | 活动截止 |
| 4 | 草稿超过 24 小时未提交 | 团长 | 状态为草稿且 `update_time` 超 24 小时 | 提交审核或删除草稿 |
| 4 | 举报或申诉有处理结果 | 提交人 | 关联记录状态转为已结案 / 处理成功 / 处理失败 | 用户点击查看后关闭 |

**关键架构约束（务必写进 `DATA_MODEL`）**：

> 待办是**派生视图，不建待办表**。全部条目由 `grouporder-activity`、`grouporder-order`、`grouporder-report`、`grouporder-bind-appeal` 的现有字段按上表规则实时查询拼装。只有"用户已关闭"这一个状态需要落库，用一张极轻的 `grouporder-todo-dismiss`（`uid` + `todo_key` + `dismiss_time`，`todo_key` 形如 `activity_offline:<activity_id>`）记录。
>
> 若建一张真正的待办表，它必须与活动状态、订单状态、治理状态、举报状态四套状态机保持同步，任何一处漏写就会留下幽灵待办——这是典型的 bug 温床，且与本项目"以服务端最终状态为准"的一贯原则冲突。

**配套建议**：用 `uni.setTabBarBadge` 在「接龙」tab 上显示未关闭的优先级 1–2 待办数量。这是在不做订阅消息的前提下，唯一能让用户"回来就看见"的手段。

**新增页面**：M-27 待办事项（接龙 tab 的默认子页）。

### C-04　商品归属：`activity_id` 必填 vs 商品属于用户（方案 A）

**现状**：`grouporder-goods.schema.json` 的 `required` 含 `activity_id`，商品完全是活动的子对象。团长每次发起接龙都要把同样的商品名、图片、说明、单位重新填一遍——参考图的「复用历史商品」正是为解决这个问题。

**方案 A 的核心**：商品库只做**复制源**，不做引用源。详细设计见 §5。

选择方案 A 而非"活动商品引用商品库"的理由：引用模型会让库里改名改图后，历史活动的清单内容跟着变；治理下架一个库商品要连坐所有历史活动。方案 A 与项目已确立的「价格快照」「收货快照」哲学一致——**一旦成为业务记录，就与源头解耦**。

### C-05　「我的」团长工具：账号级 vs 活动级（S-3：只做入口）

**现状**：统计（M-21）与清单导出（M-24）都只能从单个活动 M-20 进入。参考图把「接龙统计」做成了账号级能力。

**方案**：M-08 增加「团长工具」分组，含一个入口：

- **我的接龙清单** → 列出本人**已截止**的活动（倒序）→ 选中后直接跳 M-24 清单预览与导出。

明确写入不做的部分，避免后续被参考图带偏：

- 不做跨活动汇总指标（不新增任何统计口径，D-037 的五个指标不变）。
- 不做跨活动批量导出。理由：会把多个活动的姓名、电话、地址汇到一个文件，敏感数据面和下载审计复杂度都显著上升，与 OPS §8 的最小范围原则冲突。
- 参考图中的「专业版 / PRO 订阅」「核销员管理」属于竞品商业化与履约能力，与 D-005（不接管资金与履约）直接冲突，不纳入首版。

### C-06　活动级交付方式（S-4：引入）

**现状**：D-013 要求每张订单都必须选一条含收货人姓名、电话、完整地址的收货信息。但熟人接龙的主流履约方式是办公室自取、同小区自提——这些场景下完整地址是无意义的强制字段，而正是这个字段撑起了整套敏感资料治理需求。

**方案**：新增 D-060，活动增加 `delivery_type`：

| 值 | 含义 | 订单需要的字段 | 清单输出 |
|---|---|---|---|
| 1 | 送货上门 | 收货人姓名 + 电话 + 完整地址（沿用现状地址簿） | 含地址列 |
| 2 | 自提 | 收货人姓名 + 电话 | 不输出地址列 |

- 团长在 M-10 创建活动时必选，默认「送货上门」，发布后不可修改（已有订单的快照口径必须稳定）。
- 自提活动的 M-14 不进入 M-15 地址簿选择，改为就地填写/选择姓名与电话。
- 电话在自提活动中**仍然必填**：团长分货时需要联系方式，且它是订单去重与核对的唯一稳定字段。

**影响面**：

| 文件 | 改动 |
|---|---|
| `DECISIONS.md` | D-013 改写（地址簿仍维护完整地址，但自提活动不强制选用）；新增 D-060 |
| `PRD.md` | §5.6 收货信息、§8.3 参与接龙验收标准 |
| `UX_FLOW_SPEC.md` | F-M04、F-M05 增加自提分支 |
| `DATA_MODEL.md` | `activity` 增 `delivery_type`；`order` 的收货地址快照字段由必填改条件必填 |
| `OPS_ADMIN_REQUIREMENTS.md` | §8.1 敏感范围注明自提活动订单不含完整地址 |
| 隐私指引 | 可改写为"仅在送货上门的活动中收集收货地址"，合规表述明显更优 |

### C-07　分享进入的返回栈与 tabBar 的硬约束（文档未覆盖）

这不是产品选择，是微信小程序的技术事实，必须写进 UX 文档，否则开发阶段一定会返工。

**约束 1：分享卡片进入是单页启动。** 用户从群卡片进 M-13 时，页面栈深度为 1，`navigateBack` 会失败。左上角返回必须判断：

```
getCurrentPages().length === 1  →  uni.switchTab 到「接龙」tab
否则                            →  uni.navigateBack
```

**约束 2：tabBar 页面只能用 `switchTab` 进入，且不能带参数。** 「发起接龙」作为 tab 页意味着它无法通过 `navigateTo('/pages/activity/edit?id=xxx')` 进入。因此：

- 「发起接龙」tab = **新建态**的 M-10。
- **编辑草稿必须是另一个页面**（M-10 的编辑态，非 tabBar 页），从「我发起的」列表 `navigateTo` 进入。
- 需要定义：点「发起接龙」tab 时若已存在未提交的草稿怎么办？**建议**：顶部显示一条「你有 1 个未完成的接龙草稿，继续编辑 / 忽略」提示条，表单本身保持新建态。这比强制跳转到草稿更符合 tab 的语义。**此项需产品负责人拍板。**

**约束 3：tabBar 最多 5 项**，当前 3 项没有问题；中间「发起接龙」的凸起圆形按钮（参考图）需要自定义 tabBar 组件实现，不能用原生 tabBar 配置——这会带来一点额外工作量，也意味着 `setTabBarBadge` 要改用自定义组件的状态管理。

## 4. 商品库详细设计（方案 A）

### 4.1 新增表 `grouporder-goods-lib`

| 字段 | bsonType | 必填 | 说明 |
|---|---|---|---|
| `_id` | objectId | - | |
| `uid` | string | ✓ | 归属用户，`foreignKey: uni-id-users._id` |
| `name` | string | ✓ | 1–50 字，与 `goods.name` 同约束 |
| `description` | string | | ≤500 字 |
| `cover_image` | file | ✓ | 与 `goods.cover_image` 同约束 |
| `detail_images` | array&lt;file&gt; | | ≤9 张 |
| `unit` | string | ✓ | 默认「份」 |
| `last_price` | int | ✓ | 上次使用的单价（分）。**仅作为复用时的预填值，不是当前价** |
| `last_used_time` | timestamp | ✓ | 用于「最近使用」排序 |
| `use_count` | int | ✓ | 被复用次数，默认 0 |
| `img_check_status` | int | ✓ | 与 `goods.img_check_status` 同枚举 |
| `governance_blocked` | int | ✓ | 0 正常 1 不可复用（见 §4.4），默认 0 |

索引：`uid + is_deleted + last_used_time`（列表查询）、`uid + name`（同名去重）。

### 4.2 写入时机：自动沉淀，不需要用户操作

团长在 M-11 保存商品时，服务端同步写入商品库：

- 同一 `uid` 下**不存在同名**记录 → 新建一条。
- 存在同名记录 → 只更新 `last_price`、`last_used_time`、图片与说明，`use_count` 不变。

不设"保存到商品库"按钮。参考图里没有这个动作，用户的心理预期是"以前填过的应该自动能调出来"——多一个按钮只会让大部分人的商品库永远是空的。

### 4.3 读取时机：复制，不是引用

M-10 的「复用历史商品」→ M-28 历史商品选择页（按 `last_used_time` 倒序，支持多选）→ 确认后，为每个选中项在 `grouporder-goods` **新建一条记录**：

| 字段 | 取值 |
|---|---|
| `activity_id` | 当前活动 |
| `name` / `description` / `cover_image` / `detail_images` / `unit` | 从库复制 |
| `price` | 预填 `last_price`，**团长必须确认**（不同批次价格常变） |
| `img_check_status` | 复制库中状态；已通过的不重复送检，节省接口调用 |
| `total_stock` / `per_user_limit` | 按新商品初始化，**不从库继承**（库存是一次性的，继承会造成误发） |
| `sold_qty` / `ever_ordered` / `governance_status` | 一律初始化为 0 |

复制完成后两者完全独立：改活动商品不回写库，改库不影响任何已有活动。

**`grouporder-goods` 表零改动**——这是方案 A 相对引用模型最大的收益，已生成的 schema 与索引不需要动。

### 4.4 治理联动（方案 A 唯一的新增治理点，必须落实）

若不处理，存在一个真实漏洞：违规商品被运营下架后，团长可以从商品库无限复制到新活动，绕过治理。

**规则**：运营执行商品治理下架（A-09）时，服务端按 `发布者 uid + 商品名` 反查商品库，命中记录置 `governance_blocked = 1`。该记录在 M-28 列表中显示为不可选并说明原因，复制接口一律拒绝。

需要同步写入 `OPS_ADMIN_REQUIREMENTS.md`：§6.1 下架动作补充这一项反写；§12 日志事件补充「商品库记录标记为不可复用」。

### 4.5 图片检测

库中图片在首次保存商品时已随活动送检。复用时若 `img_check_status = 1`（通过）则直接复制状态，不重复送检；其余状态一律按新图重新检测。活动整体仍走 D-043 的发布审核，本优化只影响图片接口的调用量。

## 5. 连锁影响：废止 D-047 之后，发布审核的成本收益需要重估

这是本轮**最值得注意**的一处，因为它不在你提出的七点里，但由 S-1 直接导出。

D-043 确立了"提交发布 → 审核中 → 审核通过才可分享下单"。在有公开活动列表的前提下，这条规则是必要的：公开陈列意味着平台对内容负更重的责任。

**废止 D-047 后，这个前提消失了**，而代价变得很扎眼：

- 团长在微信群里说"我发个接龙"，然后要等平台放行才能把卡片扔进群。人工审核模式下这个等待没有上界。
- 熟人场景的接龙常常是临时起意、当天截止的（参考图的默认截止时间就是当天 18:00），审核延迟会直接杀死这个场景。
- 首版审核量约等于活动量，而 D-024 估算日增 500 个活动——人工模式意味着每天 500 次人工操作，这个运营成本没有在任何文档里被计算过。

**建议**（需拍板）：保留 D-043 的审核状态机与 D-057 的双模式配置不动，只把**首版默认值设为自动审核**——文字检测通过即进入进行中，图片按 D-058 异步回调命中后转治理下架。人工审核模式保留为运营后台的一个开关，在出现集中违规时启用。

这样治理能力一条不少（检测、举报、下架、发布限制、审计全部保留），但团长的体感从"发起后等待"变成"发起即可分享"。

**另一项附带收益**：无公开商品陈列，产品形态更接近"信息收集工具"而非"电商平台"，这对 `CATEGORY_VERIFICATION.md` 要核验的 P1-09 / B-01 是明确的利好。建议把"无公开列表、无发现推荐搜索、活动仅通过分享入口访问"写进该文档，作为向微信说明产品形态时的表述依据。
