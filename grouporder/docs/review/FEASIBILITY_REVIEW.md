# 群接龙购物小程序 可行性评审与优化建议

- 文档版本：v0.1
- 文档状态：外部评审意见，**不是项目事实**；条目经产品负责人确认后才写入 PRD / DECISIONS
- 评审对象：`README.md`、`docs/product/PRD.md` v0.3、`docs/product/DECISIONS.md` v0.3、`docs/product/OPS_ADMIN_REQUIREMENTS.md` v0.1
- 评审日期：2026-09-08
- 编号规则：B = 阻断级（下一步前必须解决）、H = 高、M = 中

---

## 1. 总体结论

**技术可行性高，产品逻辑质量在同类文档中属于中上，但项目当前的真实风险不在技术，而在三处：合规主体、范围膨胀、商业前提未验证。**

三句话概括：

1. 这套业务规则**能做**。削减后的 MVP 规模约 8～10 个页面、15 张表左右，单人 4～6 周可交付；并发、幂等、快照、导出安全等硬骨头文档已经想清楚了。
2. 这套业务规则**目前不一定能上线**。「任何用户都能发布带价格和库存的商品」这个形态，与「个人 / 个体工商户主体」的组合存在硬冲突（见 B-01），而这是唯一的单点否决风险。
3. 这套业务规则**已经写得太多了**。运营后台需求（439 行）体量超过主产品，服务的却是首版接近零的举报量；用户名密码登录体系为一个已被明确排除的目标（跨端）引入了 6 条链路。文档在几轮角色评审中只增不减，是当前最需要处理的趋势。

### 可行性分维度判定

| 维度      | 判定          | 说明                                                                                     |
| ------- | ----------- | -------------------------------------------------------------------------------------- |
| 技术实现    | 高           | 无技术难点。D-024 的容量（单活动 500 人 / 50 商品 / 日增 500 活动 / 5 万用户）用单台应用服务器 + 单库即可，无需分库分表、消息队列或缓存集群 |
| 产品逻辑自洽性 | 中上          | 主干自洽，但存在 2 处规则冲突和 1 处字段语义未定义（H-01、H-02、H-03）                                           |
| 合规与上线   | **低 / 未验证** | 主体与类目路线大概率不成立；数据留存策略未定导致隐私政策无法定稿                                                       |
| 商业价值    | **未验证**     | 相对成熟竞品是「功能更少」而非「定位不同」，尚无一条来自真实团长的验证                                                    |
| 文档工程质量  | 中           | 有决策编号和变更记录，但无术语表、无状态机、验收标准未编号、无追溯矩阵、无 git 版本控制                                         |

## 2. 阻断级风险

### B-01　主体与服务类目路线大概率不成立

**现状**：D-023 与 P1-09 的结论是「原型用个人主体，正式上线优先个体工商户，架构设计前核验类目」。

**核验结果**：

- 微信小程序的「电商平台」和「商家自营」两个类目**仅开放给非个人主体**，个人主体完全不可选。
- 「电商平台」类目通常要求《增值电信业务经营许可证》（EDI，在线数据处理与交易处理业务）。EDI 的申请主体须为公司法人，个体工商户不具备申请资格。
- 个人主体可选类目集中在工具、生活服务、教育、餐饮、体育、商业服务等，不含任何电商类目。

**结论**：本产品「任何用户都可以发布带价格、库存、限购的商品，其他用户下单」的形态，在审核视角下**高度可能被判定为 UGC 电商平台**。一旦被这样判定：

- 个人主体：直接不可选，原型阶段的类目结论完全无参考价值（M-07）。
- 个体工商户：拿不到 EDI，仍然不可行。
- 唯一可行主体：公司 + EDI。这与 D-023 的路线冲突，且大幅提高时间与资金门槛。

**建议**（按优先级）：

1. **重新定位为「非交易信息工具」并使之名实相符**，按「工具 > 预约/报名」或「生活服务」类目提审。这是与产品实质一致的路线，不是规避审核：平台确实不发生交易、不结算资金、不担保成交。为此需要在产品语言与字段上贯彻：
   - 金额字段一律呈现为「预估金额」，且不作为应付金额
   - 「订单」在用户可见文案中改为「接龙记录 / 报名记录」
   - 「库存」改为「可接数量」，「商品」可保留但配合非交易说明
   - 活动详情与提交页固定展示「本平台不收款、不发货、不担保成交」
2. **提审前用目标主体口径（而非个人主体）核验类目**，并把微信开放社区的问询记录或客服答复截图归档到 `docs/compliance/`。
3. **准备 Plan B 并提前评估成本**：若审核坚持要求电商平台类目，可选路径是（a）公司主体 + EDI，（b）收缩为「单一发起人自营」形态（D-001「任何人都能发起」是被判平台的核心特征），（c）放弃小程序改做 H5 / 公众号内网页。三条路都会显著改写 PRD，因此**必须在 UX 设计前定论**，不能等到架构阶段。

**与现有流程的冲突**：PRD §13「下一步」把类目核验列为第 1 项是对的，但项目实际已经先产出了 439 行运营后台需求。这是优先级倒置——运营后台的形态本身取决于最终主体与类目。

### B-02　数据留存策略（P1-07）必须前移，它是提审的必要材料

**现状**：产品已确认收集收货人完整姓名、电话、完整收货地址（D-013），并要求隐私保护指引说明用途（PRD §10）；但 P1-07（保存多久、如何注销和删除）在 DECISIONS 和运营后台文档中都被标记为「待合规确认」，OPS §15 明确「架构和开发不得自行固化删除、匿名化或保留策略」。

**问题**：隐私政策 / 隐私保护指引必须写明各类个人信息的**保存期限**和**注销后处理方式**，这是小程序提审的必填内容。P1-07 未定 ⇒ 隐私指引无法定稿 ⇒ 无法提审。它不是「后续合规专项」，而是与 B-01 同级的前置项。

**建议**：本周内给出一版可执行的默认策略（宁可先定后改，也不要留空），例如：

- 活动与接龙记录：活动截止后保留 12 个月，之后删除收货信息快照、保留脱敏统计
- 收货信息（用户维护的）：账号存续期间保留，用户删除即删
- 举报与处置记录：3 年
- 审计日志：1 年
- 注销：7 天冷静期后删除账号与收货信息，已参与活动的记录匿名化保留（保护团长的历史清单完整性）
- 例外：存在举报、争议或法定义务时暂停删除

### B-03　商业前提未做任何验证

**现状**：PRD §11 的竞品调研是公开资料研读，且诚实声明「本轮没有实际操作上述小程序」。§12 的成功指标是过程指标（发起成功率、参与完成率），没有「用户是否愿意用」的验证指标。

**问题**：本产品相对群接龙 / 快团团的差异是**没有支付**。这在范围控制上是正确决策（D-005），但在用户价值上是「功能更少」。文档没有回答：一个团长为什么不用免费且功能更全的快团团？

存在合理答案，但都需要验证而非假设，例如：

- 公司 / 社团 / 楼栈内部的福利团、代购，钱本来就线下走（微信转账、报销、代收），走电商平台反而多一层
- 不需要商家资质、不被平台抽佣、不担心资金链路合规
- 群接龙 / 快团团把团长引导向经营，而熟人场景的团长只想统计一次

**建议**：在进入 UX 前，用 1～2 周做最小验证——找 3～5 个真实存在的组织者（同事、小区群、兴趣群里正在手工接龙的人），问三个问题：现在怎么统计、为什么不用快团团、如果有个只统计不收钱的工具会不会用。把结论写进 `docs/product/USER_RESEARCH.md`。这一步的成本是几天，避免的是几个月。

## 3. 规则冲突与缺陷（高）

### H-01　每人限购与「为多个收货人下单」直接冲突

- D-012：每人限购按同一平台用户在该活动中的**全部有效订单合计**计算，「拆分为多张订单不能绕过限购」。
- D-013 / D-014：设计多条收货信息与多张订单的目的，正是「为不同收货人分别下单」（PRD §7 用户故事明确写了这一条）。

**冲突**：帮 3 户邻居各订 2 件，共 6 件；若团长设限购 2，则代订场景被完全挡死。而代订恰恰是熟人团购最常见的行为之一。两条决策在文档里各自成立，合在一起互相取消。

**需要产品负责人决策**，三个选项：

| 选项 | 规则 | 代价 |
|---|---|---|
| A | 限购按**平台用户**合计（现状） | 代订不可用；用户会用小号或换人下单绕过，反而更难统计 |
| B | 限购按**收货信息（收货人姓名+电话）**合计 | 符合直觉，代订可用；可被伪造收货人绕过，但熟人场景下滥用成本高、动机低 |
| C | 团长按活动选择限购口径 | 灵活，但增加一个团长要理解的概念 |

倾向 B：限购在熟人场景的真实目的是「别一个人买光」，而「一个人」在语义上更接近「一户 / 一个收货人」而不是「一个微信号」。若选 B，D-012、PRD §5.3、§8.3 三处措辞都要改。

### H-02　「库存」字段语义未定义，文档内两种理解并存

同一节（PRD §5.3）出现互相矛盾的表述：

- 「库存在接龙提交成功时**扣减**，取消时返还」→ 库存 = 剩余可售数量
- 「团长可以增加库存；**减少后的库存不得低于已接龙数量**」→ 库存 = 总量
- 「恢复后……库存不得低于已有接龙数量」→ 总量

**这是必然产生 bug 和规则争议的那类缺陷**：开发按第一种理解实现，团长按第二种理解操作，改库存时数字对不上。

**建议**：明确拆成两个字段，从 PRD 层面固定口径：

- `总库存 total_stock`：团长设置的上限，只有团长能改，不得低于 `已售`
- `已售 sold_qty`：全部有效明细数量之和，由系统维护
- `剩余 = total_stock - sold_qty`：只用于展示和校验，不落库为可写字段
- 「扣减」一词从 PRD 中删除，改为「`已售` 增加」；取消时「`已售` 减少」

顺带解决 M-11。

### H-03　永久锁价（D-018 / D-026）与价格快照机制重复，只留下了副作用

- PRD §5.5 已确认「每条接龙明细保存**提交时价格快照**，保证历史金额可追溯」。
- D-018 / D-026 又规定：商品一旦产生过成功接龙记录，**即使记录后来全部取消或作废**，也永久不能改价或删除。DECISIONS §6 给出的理由是「历史订单金额失真」。

**问题**：有了价格快照，改价**在原理上不可能**让历史订单金额失真。锁价规则要防的问题已经被快照解决了，它剩下的唯一实际效果是：团长把 5 元误写成 50 元、一个人下了单，价格就永久锁死，唯一出路是停售该商品 + 新建一个同名商品 + 让已下单的人重新下单。这在熟人群里是很高的摩擦，而输错价格是极高频的操作错误。

**建议**：改为——

- 允许改价，但改价前二次确认，明确提示「已提交的 N 张订单按原价 X 元保留，不受影响」
- 改价记录操作人、时间、前后值（这一条文档已有）
- 若担心团长恶意抬价：可加「改价后活动详情显示价格调整提示」，或限制涨幅需填原因
- 删除保持禁止（有历史引用的商品不应删除，这条是对的）——但可以「隐藏」

若产品负责人坚持锁价，则应反过来简化：既然价格永不变，快照机制就是冗余的，PRD §5.5 可以删掉快照要求。**两者留一个，不要都留。**

### H-04　用户名密码登录体系应从首版删除

D-029～D-031 引入了：注册、密码存储与校验、微信一对一绑定、双方均有数据时拒绝绑定、通过微信重设密码、未绑定账号无密码找回。它直接催生了运营后台的：

- 「账号与隐私专员」角色（OPS §3.2 整列）
- §4.6 账号绑定申诉页
- §9 账号解绑与重新绑定（整章，含 6 步链路与并发规则）
- §13.5 一整组验收标准

**代价与收益不成比例**：

- 首发平台是微信小程序，入口是群分享卡片，用户 100% 已在微信内。微信授权登录就在手边。
- 唯一的收益是「未来跨端时账号可迁移」，而 §4.2 明确「跨平台客户端开发」不属于首版。这是为一个已排除的目标预付成本。
- 「未绑定微信的账号首版不提供自动密码找回」意味着：用户注册了账号、忘了密码、且没绑微信 ⇒ 账号永久丢失，且他可能已经是某个活动的团长。这是会真实发生的坑。
- D-031「双方均有业务数据时拒绝绑定且不合并」会产出一类无解的客服工单：用户两边都有数据，系统告诉他「请继续使用原账号」——但他要的正是合并。

**建议**：首版**只做微信授权登录**。删除 D-029～D-031，改为一条决策：「首版仅支持微信授权登录；跨端与账号体系在确有第二个平台时再设计，届时以微信身份为主账号做扩展」。连带删除运营后台 §4.6、§9、§13.5 和「账号与隐私专员」角色的绑定职责。

这一刀是当前**投入产出比最高**的削减：约减少 6 条链路、1 个后台角色、2 章需求。

### H-05　运营后台过设计，体量超过主产品

OPS v0.1 规定了 4 个角色 × 20 行细粒度权限矩阵、敏感权限二次验证、举报 5 状态流转 + 复核、内容检测复核 4 状态、活动治理状态独立建模、敏感资料按事项受控解敏、Excel 生成与下载事件审计、9 类必记日志 × 9 个字段。

按需求规模估算：主产品 MVP（PRD §4.1 的 17 项）约 4～6 周；这套运营后台按现有规格实现约 4～8 周。也就是说**给一个还没有用户的产品，配了一个和产品本身一样大的治理系统**。

具体的过设计点：

1. **权限矩阵在小团队下只产生摩擦、不产生安全**。§3.2 规定超级管理员「否，除非兼任」才能检索活动 / 处置内容 / 看审计日志。在 1～2 人的团队里，结果是同一个人给自己开 4 个角色并全部兼任——最小权限原则被形式化执行，实质安全为零，但登录、切换、二次验证的成本全部真实存在。
2. **「审计查看者」角色没有人来担任**。
3. **举报 5 状态 + 复核流程**服务的是首版每月可能 0～1 件的举报量。领取、处理中、结案、复核中、复核完成——用一张列表 + 「下架 / 忽略」 + 备注就够了。
4. **Excel 审计（§4.7、§10、§13.6）是一整套独立子系统**，产出是「谁在什么时候生成/下载了清单」。首版可以退化为：在通用日志表里记一行，需要时查库。
5. **敏感资料受控解敏（§8）** 概念正确，但首版可用更简单的等价实现达到同样效果：列表和详情一律脱敏 + 完整字段不做后台入口（真需要时查库并留 SQL 记录）。这直接消掉二次验证、事项关联、原因填写、授权范围、会话失效重校验五组需求。

**建议的首版运营能力**（预计 3～5 天而非 4～8 周）：

| 保留 | 删除或推迟 |
|---|---|
| 1 个内部运营账号（可 2 个：运营 + 只读） | 4 角色权限矩阵、角色分别授权 |
| 举报列表：待处理 / 已处理（2 状态） | 领取、处理中、复核中、复核完成 |
| 活动下架 / 恢复（保留治理状态与业务状态分离的设计，这条是对的） | 单商品下架仍缺失，见 M-08 |
| 发布者：警告 / 禁止发布 / 解除（3 种，不分临时永久） | 临时限制的起止时间管理 |
| 一张统一操作日志表（操作人、时间、对象、动作、原因、前后状态、请求 ID） | 9 类事件分别建模、9 字段强约束、Excel 事件专项审计 |
| 列表与详情默认脱敏 | 二次验证、受控解敏、事项关联、访问审计 |

同时保留 OPS §2.2「运营不得代替团长经营」这条边界——它是文档里最有价值的约束之一，应原样保留。

### H-06　首版无任何通知，导致举报与申诉链路只写不读

D-032 确定首版不做订阅消息，PRD §4.2 也排除。这在参与者侧问题不大（团长会在群里说）。但以下场景**没有任何触达手段**：

- 举报处理结果（OPS §5.1 第 7 步：「用户在小程序内查看举报处理结果」）
- 绑定申诉结果（OPS §9.2 第 6 步，同上）
- 团长取消了活动 / 活动被平台下架
- 参与者的订单被团长作废

举报人举报完就离开了小程序，没有任何理由再回来查结果。**这意味着精心设计的举报闭环，用户端实际上永远看不到。**

**建议**：二选一，不要中间态。

- A（推荐，配合 H-05）：承认首版无触达，因此把举报流程简化到与之匹配的程度——用户举报后即时提示「已收到，我们会处理，处理结果不单独通知」，删除「用户可查看处理结果」相关需求与验收标准。
- B：保留结果查看，但必须做进入小程序时的强提示（首页红点 + 拦截式弹窗 + 个人中心「我的反馈」入口），并接受它的到达率很低。

顺带：订阅消息本身成本不高（一次性授权 + 模板消息），若做「活动即将截止提醒」，对参与完成率的提升可能是首版最划算的功能之一。值得重新评估 D-032，至少不要连「截止提醒」一起排除。

## 4. 其他优化点（中）

### 产品与规则

- **M-01　术语不统一。** 「接龙记录」（§5.4）、「接龙订单」（§5.4）、「接龙明细」（§5.5）三个词混用，且层级关系从未定义。§5.5 的参与人数按「有效接龙明细」去重、商品总份数按「明细数量之和」，但 §5.4 讲的是「记录」的状态。需要一张术语表明确：**活动 → 订单（一张订单一个收货信息）→ 明细（一个商品一行）**，然后全文替换到位。这是后续所有角色 Agent 误解的最大来源。
- **M-02　缺状态机。** 活动业务状态（草稿/进行中/已截止/已取消）× 治理状态（正常/已下架）× 商品状态（在售/停售/已删除）× 订单状态（有效/已取消/已作废）四套状态互相约束，规则散落在 PRD §5.2/§5.3/§5.4、§8.5/§8.6、OPS §6/§11 六处，靠纯文字已经难以自洽（例如 OPS §6.2「活动在下架期间到达截止时间的，按已截止处理，不能通过恢复重新开放」这类规则，文字表述极易漏组合）。**建议出一份状态转移表**（行=当前状态，列=事件，格=结果或拒绝原因），这一份表能替代好几页文字并暴露遗漏。
- **M-03　首页「进行中的相关活动」范围未定义。** PRD §6 首页含「进行中的相关活动」，但「相关」未定义。若包含他人活动，产品即构成公开商城，会同时（a）恶化类目判定（B-01），（b）把内容治理压力放大若干倍，（c）破坏 D-016 的熟人场景假设。**建议明确写入 PRD：首页仅展示本人发起或参与的活动，首版不提供任何发现、推荐、搜索他人活动的能力。**
- **M-04　强制完整地址的隐私成本可能不划算。** D-013 让每张订单都必须选一条含完整地址的收货信息。但熟人场景的主流履约方式是「同小区自提」「办公室自取」「团长挨家送」——前两种根本不需要地址。而正是「收集姓名+电话+完整地址」这件事，撑起了后面整套敏感资料治理、隐私政策、脱敏解敏需求。**建议：团长按活动选择履约方式**——「需要收货地址」/「自提（仅需收货人姓名 + 可选电话）」。这一个选项同时改善参与转化、缩小敏感数据面、降低合规负担，是杠杆很高的一处改动。
- **M-05　验收标准未编号，缺追溯矩阵。** PRD §8 的 60 余条验收标准是散装 bullet，无编号。对「AI 当负责人、多角色 Agent 协作」的开发方式，这是最影响可控性的缺口——无法把测试用例、页面、接口挂回验收标准，也无法判断某次改动破坏了哪一条。**建议：AC-001 起编号，并在 `docs/product/TRACEABILITY.md` 建一张 决策(D-xxx) ↔ 验收(AC-xxx) ↔ 页面 ↔ 测试用例 的对照表。**
- **M-06　「可打印清单」的目标与 .xlsx 交付形式不匹配。** 团长的实际场景是拿着手机在群里分货。微信内打开 .xlsx 需跳第三方应用，打印需要 PC。D-021 把 .xlsx 定为唯一导出，而「清单导出为长图或 PDF」被放在 §4.3 暂缓。**建议调整优先级**：小程序内清单页（已有）+ 长图分享 为主，.xlsx 为辅（给需要在电脑上做采购汇总的团长）。长图的实现成本低于 Excel。
- **M-07　用个人主体做原型期类目核验会得到错误结论。** 个人主体与个体工商户 / 企业主体的可选类目集合本身不同（见 B-01）。用个人主体验证出来的类目结论对正式上线没有参考价值。**核验必须以目标主体口径进行。**
- **M-08　运营侧缺少单商品处置手段。** OPS §4.4 明确「只允许下架或恢复整个活动；首版不提供运营侧商品编辑或单商品下架」，但一个活动可含 50 个商品（D-024）。若其中 1 个商品违规，唯一手段是下架整个活动，牵连另外 49 个合法商品和所有已提交订单——这对团长的惩罚过重，实际运营时一定会被绕过（改成私下联系团长）。**建议首版就保留「单商品下架」**（只置为不可选，不改内容、不删记录），成本很低。
- **M-09　自动截止的实现语义未定。** 「系统到时自动截止」既可以是定时任务改状态，也可以是读取时按服务端时间惰性判定。前者依赖调度器可用性，调度器挂了会出现「已过截止时间但仍可提交」。**建议在 PRD 明确：状态以服务端时间惰性判定为准，定时任务只做后置清算（生成清单、发通知等），不作为状态正确性的依赖。**
- **M-10　取消 / 作废对已线下付款的参与者没有救济路径。** D-027 允许团长取消已有有效接龙的进行中活动。由于收款在线下，参与者可能已经转账。产品无法也不应处理退款，但**必须在用户协议和取消提示里写清**：平台不收款、不担保成交，款项纠纷由双方线下解决，并提供反馈入口。PRD §10 有相近表述，建议在「团长取消活动」的二次确认文案和参与者看到的取消状态页里也显式呈现。

### 文档与工程

- **M-11　`docs/` 下没有 git 仓库。** 项目宣称「项目文件是唯一事实来源」，但没有版本控制——DECISIONS 的变更记录靠人手写，文档改动无法 diff、无法回滚、无法定位是哪一轮评审引入了某条规则。这与项目的协作方式（多角色 Agent 修改文件）严重不匹配。**建议立刻 `git init` 并逐次提交**，同时把 `.DS_Store` 加入 `.gitignore`（`docs/.DS_Store` 已在仓库目录中）。
- **M-12　README 混入了 AI 协作提示词。** 「修改超过 3 个文件时先征求确认」「每次实现后检查空值风险、**内存分配**、生命周期」——内存分配对小程序 + 服务端项目基本不适用，说明这段约束是从通用模板抄来的，不是针对本项目写的。**建议：把 AI 协作规则移到 `CLAUDE.md`，README 只保留给人看的信息**（这是什么、当前状态、文档入口、怎么参与）。
- **M-13　缺少的文档。** 按当前阶段，以下几份的缺失比「继续细化运营后台」更值得补：
  - `GLOSSARY.md`　术语表（解决 M-01）
  - `STATE_MACHINE.md`　状态转移表（解决 M-02）
  - `DATA_MODEL_DRAFT.md`　实体与字段草案（在架构阶段前，它能暴露 H-02 这类语义缺陷）
  - `USER_RESEARCH.md`　真实团长访谈结论（B-03）
  - `docs/compliance/`　类目核验记录、主体决策、留存策略（B-01、B-02）
  - `NON_FUNCTIONAL.md`　可用性目标、备份 RPO/RTO、日志留存、监控告警、成本预算——目前只有 PRD §10 一句「重要数据需要备份」
  - `ROADMAP.md`　里程碑与工期。项目目标是「真实上线」（D-010），但全套文档里没有任何时间线或人力假设
- **M-14　文档增长趋势本身需要治理。** 三轮迭代下来，PRD 从需求变成了准架构文档（并发、幂等键、公式注入、链接时效都进了 PRD），运营后台从「最低限度」长到 439 行。这是「每个角色 Agent 只会加规则、没有角色负责删规则」的必然结果。**建议在 README 的协作方式里增加一条**：每次评审除了提出新增，必须同时提出至少一项可删除或可推迟的内容，并在 DECISIONS 变更记录中标注净增减。

## 5. 值得保留的部分

以下设计质量明显高于同类文档，削减范围时**不要动它们**：

1. **幂等设计**：区分「明确的新下单意图」与「同一请求的网络重试」，前者独立幂等键、后者复用，并以订单号唯一约束兜底。这是电商类需求里最常做错的一处，文档做对了。
2. **价格快照**：每条明细存提交时单价，历史金额可追溯（与 H-03 配合使用才发挥价值）。
3. **Excel 公式注入防护**：明确要求用户可控文本不得被电子表格当作公式执行。这一条在需求文档里出现的概率很低。
4. **清单下载安全**：不使用公开固定地址、每次下载校验权限、链接有效期、过期即失效。
5. **服务端原子校验与扣减**：库存、限购、截止时刻一律以服务端事务结果为准，前端不做权威判断。
6. **业务状态与治理状态分离**（OPS §6.1、§11.1）：下架不改写活动业务状态，也不删数据。概念干净，应保留。
7. **运营不得代替团长经营**（OPS §2.2）：一条清晰有力的边界，防止后台演化成万能数据改写工具。
8. **明确不做清单**（PRD §4.2、OPS §14）：写下「不做什么」比写「做什么」更能控制范围。
9. **竞品结论不作为业务事实的自律声明**（PRD §11 末段）：诚实标注了「本轮没有实际操作上述小程序」，避免了把二手信息当事实。
10. **决策编号 + 变更记录 + 状态标记**（DECISIONS）：机制本身是好的，需要的是继续执行「建议项必须经确认才转已确认」这条纪律。

## 6. 建议的下一步顺序

当前 PRD §13 的顺序是：类目核验 → UX 页面流 → 产品审查 → 视觉 → 架构。方向对，但漏了需求验证和合规前移，且不含范围削减。建议改为：

| 步骤 | 内容 | 产出 | 阻塞关系 |
|---|---|---|---|
| 0 | `git init`，提交现有文档 | 可追溯的基线 | 立刻，无阻塞 |
| 1 | **并行**：(a) 目标主体口径的类目与主体核验（B-01）；(b) 3～5 个真实团长访谈（B-03） | `docs/compliance/CATEGORY_VERIFICATION.md`、`USER_RESEARCH.md` | **阻塞后续一切**。两项都可能改写产品形态 |
| 2 | 数据留存与注销策略定稿（B-02） | 写入 DECISIONS，P1-07 转已确认 | 阻塞隐私指引与提审 |
| 3 | **范围削减**：按 H-04、H-05、H-06 执行，并对 H-01、H-02、H-03 做产品决策 | PRD v0.4、DECISIONS v0.4、OPS v0.2。**预期文档变短，不是变长** | 依赖步骤 1 |
| 4 | 术语表 + 状态转移表 + 编号化验收标准 + 追溯矩阵（M-01、M-02、M-05） | 4 份文档 | 与步骤 3 同批 |
| 5 | UX 页面流与低保真原型 | 页面清单、流程图 | 依赖 3、4 |
| 6 | 架构设计（含削减后的最小运营能力） | 架构、数据模型、接口 | 依赖 5 |

**削减后的规模预估**：微信授权登录 + 活动/商品/订单/清单 + 最小运营能力，约 8～10 个小程序页面、2～3 个后台页面、15 张表左右。单人 4～6 周可交付可上线版本。不削减则约为 3～4 倍，且大部分增量服务于零用户量下的治理场景。

## 7. 本评审未验证的事项

以下内容评审时无法确认，需要产品负责人补充或另行核验：

1. **目标用户所在地区与主体所在地。** 项目文档默认了中国大陆语境（个体工商户、微信内容安全接口、腾讯云电商类目）。若目标用户或经营主体在境外（如新加坡），则：海外主体小程序在可选类目、部分接口能力、以及「个体工商户」这条路线上都不适用，B-01 需要按海外主体规则重新核验。**这是一个需要明确回答的前置问题。**
2. **微信平台规则的当前口径。** 本评审对类目与主体限制的核验基于官方文档与公开资料，但平台规则会变，**最终以目标 AppID 后台实际可选类目和提交审核时的答复为准**（PRD §10 已有相同免责，此处一致）。
3. **微信内容安全接口的调用前置条件。** `msgSecCheck` / `mediaCheckAsync` 对小程序状态（是否已发布）、主体类型和频率限制的当前要求未逐项核验，实施前需按 PRD §10 的链接确认。
4. **团队规模与可投入时间。** 本评审的工期估算按「单人全职」假设。若为兼职或多人，步骤 3 的削减建议应更激进。
5. **是否已有任何代码。** 评审时项目仅含 4 份 Markdown 文档，无代码、无 git 仓库。若别处已有原型，本评审的工期与削减结论需要相应调整。
