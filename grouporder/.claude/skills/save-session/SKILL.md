# save-session

把**本次会话产生、但项目文档里没有**的内容存成 memory 文件，供 clear 之后的会话恢复上下文。

## 存放位置

```
memory/
  MEMORY.md              索引，每个 memory 一行
  <SessionName>.md       本次会话的记录
```

全部位于**项目目录下**，不写入 `~/.claude`。

## 命名规则

文件名**必须使用当前 session 的名称**，不要自拟主题名。

```
memory/<session名称>.md
```

**重要限制：Agent 无法程序化读取 session 名称。** 因此执行时必须：

1. 先问用户：「这次 session 的名字是什么？memory 文件我按它命名。」
2. 用户答复后，把名称中的空格去掉作为文件名，其余字符原样保留
3. 若用户给出的名称过于笼统（如 `init`、`test`、`session1`），**提议加一个能体现工作范围的前缀**并等确认，例如 session 名为 `init`、本次主要做运营后台 → 提议 `admin-init.md`。用户不同意就用原名。

```
session「init」+ 本次做后台        →  memory/admin-init.md
session「Goods Lib v0.3」        →  memory/GoodsLibv0.3.md
```

若同名文件已存在，读取后**合并更新**，不要覆盖，也不要另起 `-2` 这类后缀。

## 判断标准：什么该存，什么不该存

这是本 skill 最关键的部分。**项目遵循「文档即事实源」**，凡是已经写进 `docs/` 的内容都不要重复记录——重复会产生第二个事实源，且会过期。

**该存：**

- 用户在对话中表达的工作方式偏好与纠正（例：不要擅自改第三方模块）
- 已做出但**尚未落进文档**的判断，以及当时的理由
- 本次会话中发现、但还没有处理完的问题线索
- 跨会话的分工约定（谁负责什么、哪些交给别的 session）
- 用户否决过的方案及否决原因——避免下次重新提出

**不该存：**

- 决策内容本身（在 `docs/product/DECISIONS.md`）
- 数据模型、字段定义（在 `docs/arch/DATA_MODEL.md`）
- 需求与规格（在 `docs/product/` 下）
- 代码结构、文件清单（读代码即可得到）
- 本次会话的流水账

判断方法：**如果读一遍 docs/ 就能知道，就不要写进 memory。**

## 文件格式

```markdown
---
name: <文件名（不含扩展名）>
description: <一句话说明这个 memory 记的是什么>
date: <最后更新日期>
---

## 本次会话做了什么

三到五行，只说结论与落点，细节指向文档。

## 需要延续的判断与约定

- 用户的工作方式偏好、纠正
- 已定但未落文档的判断及理由
- 跨会话分工

## 未完成与待办

- 尚未处理的问题，标明阻塞在哪里

## 下次恢复上下文的入口

按需列出本次涉及的关键文档路径。
```

## 执行步骤

1. **先问用户 session 名称**（Agent 读不到，必须问）。名称笼统时按命名规则提议带前缀的写法并等确认
2. 检查 `memory/<名称>.md` 是否已存在：存在则读取后合并，不存在则新建
3. 按上面的判断标准筛选内容，写入文件；frontmatter 的 `name` 与文件名保持一致
4. 更新 `memory/MEMORY.md` 索引，格式：`- [名称](文件名.md) — 一句话提要`
5. 向用户报告：存了什么、文件在哪、以及**哪些内容因为已在文档中而刻意没存**

## 恢复上下文时怎么用

新会话开始、需要接续之前的工作时：

1. 先读 `memory/MEMORY.md` 索引，找到相关的 memory 文件
2. 再按 `README.md` 的「AI 开始工作时的读取顺序」读项目文档
3. **文档与 memory 冲突时以文档为准**——memory 记的是当时的判断，文档是确认后的事实
