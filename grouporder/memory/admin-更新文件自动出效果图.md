## 需要延续的判断与约定

**最大的教训：动手前先核查框架已提供什么。**
v1 效果图自造了一整套后台外观——自研 CSS 体系、自定义表格样式、表格上方独立筛选区、文字链接式操作列。而 uni-admin 里 A-01 登录页、A-15 账号与角色权限（九个现成页面）、左侧菜单（`opendb-admin-menus` 数据驱动）、顶栏、面包屑**全部是现成的**；表格的筛选与排序本来就长在列头上（`filter-type` + `sortable`）。是用户问「这样好吗」才暴露。
**基于模板或框架的项目，第一步是盘点框架资产，再决定哪些新建。** 盘点结果与实测视觉规范已写进 `ADMIN_REUSE_MAP.md` §1～§3。

**长会话中途必须重新核对 DECISIONS。**
本会话跨 9-16～9-18。我依据会话内记忆写出的 `ADMIN_BUILD_PLAN` v0.1，把「默认脱敏」列为 L0 三条铁律之首、把 `mask.js` 与 `ops-verify.js` 列为阶段 1 的前置模块——而 **D-072 已在会话期间取消后台全部脱敏与二次验证**。磁盘上的文件已被另一执行改写为 v0.2 修正。
**产出跨越多日的文档前，先重读 `DECISIONS.md` 的最新条目与 `memory/MEMORY.md` 索引**，确认会话内记忆没有被推翻。同一批文档可能有其他 session 在并行修改，后写的会覆盖先写的。

**Bash 输出要主动控制。**
本次会话 Bash 结果占用约 168k tokens（17% 上下文）。读大文件一律用 `grep` / `head` / `sed -n` 限定范围，避免 `cat` 整个文件；批量校验用 Python 脚本只打印结论，不打印原文。

**用户的提问方式。**
用户常以疑问形式指出问题（「这样好吗」「我看不太懂」「admin 是系统自带的用户吗」），期待的是**先核查工程事实再回答**，而不是直接下结论。本次每次都先读代码再答，用户接受了这种方式。其余工作方式偏好见 `admin-init.md`，不重复。
