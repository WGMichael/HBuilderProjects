## 需要延续的判断与约定

**我在本项目的角色**（用户 2026-09-17 明确）：项目主导 + 文档与需求分析。**效果图与代码交给别的 session 执行**，我负责准备任务书、发现规格矛盾、维护文档一致性。用户说过「真正的项目代码在最后再写，不用急」。

**用户的工作方式偏好：**

- **不要擅自改第三方模块**。触发点：我为统一 uni-id-pages 版本，未确认就替换了 admin 工程 209 个模块文件，被要求完整回滚。模块升级应走 HBuilderX 插件市场。例外是 `config.js` 这类模块预留给项目的配置文件，但**升级会覆盖**，已记入 `DATA_MODEL §3` 的三项必检清单。
- 口头确认即可推进，不需要反复确认方案。
- 会重新评估已定的决策（脱敏就是前天刚定、第三天推翻的）。提出关切一次即可，用户重申后照做。

**会话记忆的约定：**

- memory **必须放在项目路径下**（`memory/`），不要写入 `~/.claude` 的系统层。我第一次放错过位置，已清除。
- 用户会在 **clear 前调用 `save-session`**，因此每次会话结束前应主动确认是否需要保存。
- 本 session 名为 **`init`**，因过于笼统，约定文件名加范围前缀为 **`admin-init`**。同名时合并更新，不覆盖、不加 `-2` 后缀。
- **我无法程序化读取 session 名称**，必须向用户询问。曾自拟主题名「后台设计与脱敏放开」被纠正。

**文档整理的偏好（2026-09-18）**：用户选择**直接删除**过程文档，不要归档目录、不要原地加废止标注。理由是 git 历史已经能追溯，留着反而占目录。**因此提整理方案时，"归档"不是用户想要的选项，直接给"删除 + 内容并入哪里"。** 规则本身已写入 `README.md` 文档入口节末尾。

用户也倾向**把功能点并入主文档**而不是让它独立成文件。并入时的分工：产品级定义与验收进 `PRD.md`，字段级规则、接口契约与 AC-* 编号进 `DATA_MODEL.md`——这样 PRD 不会被实现细节污染，AC 编号也不会丢（`update.md` 的自检在引用它们）。

**文档写法的硬性要求（2026-09-18，用户明确纠正我）**：**不要用删除线保留废止内容**。正文只列最新需求，废止的直接删除；改动历史一律放到**文档末尾的变更记录表**。我此前在 D-072 清理时大量用 `~~条目~~ 已取消` 的写法保留编号，被要求全部移除（共清 27 处）。

配套做法：删除条目时**编号不重排**（重排会让跨文档交叉引用大面积失效），空缺在变更记录里说明；但**章节号该重排就重排**（UX_STATE_MATRIX 的 §9 空缺已重排，顺带修掉原有两个 §13 的重复）。删完必须扫一遍指向被删内容的悬空引用——这次查出 `ADMIN_BUILD_PLAN` 的 A-15 任务卡仍按旧规则写验收标准、`UX_REVIEW_GATE` 把已废止的 D-047 标成「已确认」、D-043 与 D-059 直接矛盾等多处。

**用户否决过的方案，不要再提：**

- 运营后台削减版（评审 H-05）—— 用户明确要完整版，理由是「要不我不会这么细看文档和你讨论这么多」
- 敏感资料脱敏与二次验证 —— D-072 已全面取消，理由是单人团队成本收益不成比例
- 把 `user/list.vue` 拆成两个页面 —— 改为在同一页加身份筛选器

**一个反复出现的教训**：不要用关键词统计来判断文档**覆盖度**，会严重误导。我曾据此误判「13 个后台页面覆盖偏薄」，精确检查后发现规格其实相当完备（§12.1 有 10 类对象状态表、§12.2 有 13 条通用异常）。

**与上一条相反的一面（2026-09-18 新增）**：判断覆盖度不能用关键词，但**清理一条被推翻的决策必须用关键词全 docs 扫一遍**。D-072 定下后只改了 DECISIONS、OPS、DATA_MODEL、KNOWN_ISSUES 四份，`UX_STATE_MATRIX`、`UX_REVIEW_GATE`、`ADMIN_BUILD_PLAN` 三份一处没动，`ADMIN_BUILD_PLAN` 里 22 处残留还把 `mask.js`、`ops-verify.js` 列为阻塞全部业务页的前置——批次 B 开工时执行 session 会照着建两个已作废的模块。**推翻一条决策后，扫 `脱敏|二次验证|解敏|<废止的决策号>` 这类关键词，逐文件确认，是必做动作。**

**另一个判断（2026-09-18）**：取消一项保护机制时，要分清它保护的东西是否也一起消失了。D-072 取消脱敏，但审计链路完整保留——约束从「看不见」换成了「看得见但全记录」。修订文档时若把两者一起删掉，等于把 D-072 读成「后台对数据没有任何约束」，这是误读。为此在效果图任务书里新增了红线⑨。
