# Performance Workflow · 性能优化工作流

> 现状：mock 骨架期，谈性能**为时尚早**。本篇先作 checklist 桩，等真机数据/真实接口上来后再逐项展开。
> 原则：先测量，再优化；不要过早优化。

## 什么时候才启动性能优化

- 商品/订单接了真实后台，数据量真实起来后。
- 微信开发者工具「性能」面板或真机出现明显卡顿、首屏慢、包体告警。
- 上线前做一次体检。

## 小程序常见优化点（届时逐项查）

**加载 / 包体**

- [ ] 分包加载：非核心页面（订单、地址、后台入口）拆分包，减小主包体积（微信主包 2MB 限制）。
- [ ] 图片走 CDN + 指定尺寸 + 懒加载；避免超大图直传。
- [ ] 首屏请求合并：首页已用 `Promise.all` 并发拉 banner/分类/热销，保持这一模式。

**渲染 / 数据**

- [ ] 长列表用分页加载 + `scroll-view` / 虚拟列表，避免一次性渲染上百项。
- [ ] 减少一次性 setData / 响应式数据体积；只把要渲染的字段放进响应式对象。
- [ ] 图片列表加占位，避免布局抖动。

**数据层**

- [ ] 低频且不变的数据（分类、banner）做内存/本地缓存，减少重复请求。
- [ ] 请求失败重试 / 超时（`utils/request.ts` 已有 timeout，可加重试策略）。

## 测量手段（本项目现实版）

- 微信开发者工具：Performance 面板、Network、真机调试的体验评分。
- 无 CI/自动化压测；以真机手动体验 + 面板数据为准。
