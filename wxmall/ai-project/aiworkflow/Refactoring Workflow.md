# Refactoring Workflow · 重构工作流

> 原则：**行为不变，只改结构**。本项目的分层边界（`db` / `IDataSource`）是重构的天然保护伞。

## 何时重构

- 页面里出现重复的 UI 片段（如商品卡片）→ 抽组件。
- 数据处理逻辑塞在页面里 → 下沉到数据层或 store。
- 某文件过长、职责不清 → 拆分。
- 切后台前的准备（把散落逻辑收拢到 `api/` / `datasource`）。

## 硬约束（重构不许破坏的东西）

1. **对外行为不变**：页面调用方式、`IDataSource` 方法签名不变。
2. **改动藏在边界后**：优先在 `data/` / `store/` / 组件内部改，页面尽量零改动。
3. **mock 输出一致**：重构前后，同一次调用 `db.xxx()` 返回的数据结构/内容不变——这是单人项目最实用的"回归基准"。
4. **两端同步**：若动了数据方法，mock 和 cloud 一起改。

## 流程

```
定目标 → 圈定边界(尽量不动页面) → 小步改 → 每步验证行为不变 → 更新文档
```

1. 一句话写清重构目标和"完成后什么样"。
2. 圈定影响范围，确认不外溢到页面接口。
3. 小步提交，一次只做一类改动（抽组件就只抽组件，别混入改逻辑）。
4. 每步用微信开发者工具验证主链路行为不变；`USE_MOCK` true/false 都过。
5. 若重构调整了约定，更新 `CLAUDE.md` / 相关 Workflow。
